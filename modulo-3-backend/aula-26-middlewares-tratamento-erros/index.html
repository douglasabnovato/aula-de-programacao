⛓️ 1. A Cadeia de Middlewares Globais

🎯 Desafio

O suporte da transportadora fictícia Serra Log recebe a reclamação "o sistema deu erro às 14h" e ninguém consegue achar, no log, qual requisição foi. As linhas de várias pessoas se misturam e não há como ligar uma à outra. Como marcar cada requisição do começo ao fim para rastrear um problema específico?

Middleware é uma função que roda no caminho entre a requisição e a resposta, na ordem em que foi registrada. Na aula 21 ele apareceu como um log simples; aqui a cadeia vira infraestrutura: identificador por requisição, tempo de resposta medido e log estruturado em JSON.

  • 📄 Writing middleware — Express A assinatura (req, res, next) e o que acontece quando next não é chamado.
  • 📄 Using middleware — Express Middleware de aplicação, de roteador e de erro, e por que a ordem de registro importa.
  • 📄 Crypto — Node.js Onde está crypto.randomUUID, usado para gerar o identificador de cada requisição.
  • 📄 Logging Cheat Sheet — OWASP O que registrar, o que nunca registrar e por que log estruturado facilita a investigação.

  • ▶️ Entendendo de uma vez o que é uma Middleware | Mini Curso Node #05 - Middleware Tsunode · 13:54 — Explica o conceito de middleware no Node e como a requisição passa de um para o outro.

Siga os 10 passos abaixo para construir a prática aplicando os conceitos do bloco:

  1. Configuração do Ambiente: no projeto da aula 25, crie a pasta src/middlewares/ e confirme com npm ls express que a versão instalada é a 5.
  2. Identificador da Requisição: em requestId.js, gere crypto.randomUUID(), guarde em req.id e devolva no cabeçalho X-Request-Id.
  3. Reaproveitando o Id Recebido: se o cliente já mandou um X-Request-Id curto e válido, use o dele — é assim que um mesmo id atravessa vários serviços.
  4. Medindo o Tempo: em logRequisicao.js, marque process.hrtime.bigint() na entrada e escute res.on('finish').
  5. Log em JSON: no finish, imprima uma linha com JSON.stringify contendo id, método, rota, status e duração em milissegundos.
  6. Erro Provocado: registre o middleware de log depois das rotas, faça uma chamada e observe que nada é impresso; volte-o para o topo e explique por quê.
  7. Esquecendo o next: remova proximo() do requestId, faça uma chamada e veja a requisição ficar pendurada; devolva a chamada.
  8. Middleware de Roteador: aplique um middleware só nas rotas de tarefas com router.use e compare com o global.
  9. Organização: exporte os middlewares por src/middlewares/index.js e deixe o app.js legível de cima a baixo, na ordem em que a requisição passa.
  10. Validação e Testes: faça três chamadas, confira o X-Request-Id na aba Rede, encontre cada uma no log pelo id e registre no README a ordem da cadeia.

🚨 2. Erros de Domínio e Resposta Padronizada

🎯 Desafio

Na API da Serra Log, uma rota devolve { erro }, outra { message } e uma terceira devolve o stack trace inteiro com o caminho das pastas do servidor. O app mobile precisa de um tratamento diferente para cada rota. Como fazer toda falha sair da API no mesmo formato e com o status certo?

Nem todo erro é 500: tarefa inexistente é 404, regra violada é 422, entrada malformada é 400. Classes de erro próprias carregam o status junto, e um único middleware de erro traduz tudo para o formato Problem Details da RFC 9457, escondendo do cliente o que é detalhe interno.

  • 📄 Error Handling — Express O middleware de quatro argumentos e como erros síncronos e assíncronos chegam até ele.
  • 📄 Upgrade to Express v5 — Express A mudança que faz Promises rejeitadas irem direto para o tratador de erro.
  • 📄 Error — MDN O objeto Error do JavaScript e como estendê-lo com class ... extends Error.
  • 📄 RFC 9457 — Problem Details for HTTP APIs O formato padrão de erro com type, title, status, detail e instance.

Siga os 10 passos abaixo para construir a prática aplicando os conceitos do bloco:

  1. Configuração do Ambiente: crie src/erros/AppError.js com uma classe que estende Error e guarda status e titulo.
  2. Erros Específicos: derive NaoEncontrado (404) e RegraViolada (422) de AppError no mesmo arquivo.
  3. Lançando na Camada Certa: troque o return res.status(404) do controlador por throw new NaoEncontrado('Tarefa', id) no serviço.
  4. Rota Assíncrona: escreva o controlador com async e sem try/catch: no Express 5, a Promise rejeitada já chega ao middleware de erro.
  5. Tradutor Único: em erro.middleware.js, use o status do erro quando ele for AppError e 500 em qualquer outro caso.
  6. Formato Padronizado: responda com Content-Type: application/problem+json e os campos type, title, status, detail e instance.
  7. Ligando ao Rastreio: inclua o req.id da prática anterior no corpo do erro e na linha de log.
  8. Erro Provocado: lance new Error('falha ao conectar no banco') numa rota e confira que o cliente recebe só "Erro interno", enquanto a mensagem e o stack ficam no log.
  9. Rota Inexistente: registre, depois das rotas e antes do middleware de erro, um handler final que transforma qualquer caminho desconhecido em NaoEncontrado.
  10. Validação e Testes: provoque 404, 422 e 500, compare os três corpos e escreva um teste Supertest que verifica o content-type application/problem+json.
Concluiu todos os passos?

✅ 3. Validação de Entrada com Esquemas

🎯 Desafio

Um parceiro da Serra Log enviou o campo prazo como o texto "amanhã" e a prioridade como 99. A API aceitou, gravou e o relatório do fim do mês quebrou. Os ifs de validação estão espalhados por seis controladores e cada um checa uma coisa diferente. Como declarar num lugar só o formato exato que cada rota aceita?

Um esquema descreve o formato esperado — tipos, limites, campos obrigatórios — e valida o dado de uma vez. Com Zod, o esquema vira um middleware reutilizável que recusa a requisição antes do controlador e aponta cada problema com o nome exato do campo.

  • 📄 Basic usage — Zod Definir um esquema e validar com parse e safeParse.
  • 📄 Defining schemas — Zod Strings, números, datas, objetos estritos e coerção de tipo.
  • 📄 Customizing errors — Zod Como escrever mensagens de erro em português para cada regra.
  • 📄 Zod — repositório oficial Código-fonte, versões e o histórico de mudanças da biblioteca.

Siga os 10 passos abaixo para construir a prática aplicando os conceitos do bloco:

  1. Configuração do Ambiente: instale npm install zod e crie src/esquemas/tarefa.esquema.js.
  2. Primeiro Esquema: declare z.strictObject({ titulo: z.string().trim().min(3).max(120) }).
  3. Campos Opcionais com Regra: acrescente prioridade: z.number().int().min(1).max(5).optional() e prazo: z.coerce.date().optional().
  4. Middleware Genérico: escreva validar(esquema), que devolve um middleware chamando esquema.safeParse(req.body).
  5. Substituindo o Corpo: em caso de sucesso, troque req.body por resultado.data — já sem espaços sobrando e com a data convertida.
  6. Campos Desconhecidos: envie um campo extra admin: true e observe a recusa causada pelo strictObject.
  7. Erro Provocado: envie prioridade: "3" como texto, leia a mensagem e decida se o contrato deve aceitar conversão ou recusar.
  8. Resposta de Validação: lance um ValidacaoFalhou (400) que liste campo e mensagem de cada problema, no mesmo formato Problem Details da prática anterior.
  9. Aplicando nas Rotas: use router.post('/', validar(criarTarefaEsquema), controlador.criar) e apague os ifs antigos do controlador.
  10. Validação e Testes: envie cinco corpos inválidos diferentes, confira que todos voltam 400 com o campo certo apontado e registre no README o esquema de cada rota.
Concluiu todos os passos?
