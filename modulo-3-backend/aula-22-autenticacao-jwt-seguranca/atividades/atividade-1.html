Cadastro e Login com bcrypt — Código de Referência

Aula 22 · Módulo 3: Backend e Banco de Dados · ByteClass

O ponto da atividade

Senha nunca é guardada, nem mesmo criptografada — é resumida com um hash lento e com salt. Um vazamento do banco não entrega as senhas.

auth.controller.js

const bcrypt = require('bcryptjs');
const servico = require('../services/usuarios.service');

const registrar = async (req, res) => {
  const { email, senha } = req.body;

  if (!email || !email.includes('@')) {
    return res.status(400).json({ erro: 'E-mail inválido' });
  }
  if (!senha || senha.length < 8) {
    return res.status(400).json({ erro: 'A senha precisa de ao menos 8 caracteres' });
  }
  if (servico.buscarPorEmail(email)) {
    return res.status(409).json({ erro: 'E-mail já cadastrado' });
  }

  const senhaHash = await bcrypt.hash(senha, 10);
  const usuario = servico.criar({ email, senhaHash });
  res.status(201).json({ id: usuario.id, email: usuario.email });
};

const login = async (req, res) => {
  const { email, senha } = req.body;
  const usuario = servico.buscarPorEmail(email);

  // Mesma resposta para e-mail inexistente e senha errada: não entregamos
  // ao atacante a informação de quais e-mails estão cadastrados.
  const senhaConfere = usuario && await bcrypt.compare(senha, usuario.senhaHash);
  if (!senhaConfere) {
    return res.status(401).json({ erro: 'Credenciais inválidas' });
  }

  res.json({ id: usuario.id, email: usuario.email });
};

module.exports = { registrar, login };

Três decisões que valem discussão

  • O fator 10 no bcrypt controla quanto tempo o hash demora. Mais alto é mais seguro e mais lento — é um ajuste, não um número mágico.
  • A resposta genérica no login parece pior para o usuário e é melhor para a segurança. Vale o trade-off.
  • O retorno do cadastro não inclui o hash. Nunca devolva ao cliente o que ele não precisa.
