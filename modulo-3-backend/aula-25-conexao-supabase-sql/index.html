🗄️ 1. Modelagem Relacional e SQL no Postgres do Supabase

🎯 Desafio

A escola de idiomas fictícia Fala Fácil guardava as tarefas dos professores numa planilha e já perdeu registros por nomes de turma digitados com grafias diferentes. Agora cada tarefa precisa pertencer a um projeto, e projeto apagado não pode deixar tarefa órfã. Como fazer o próprio banco recusar dado inconsistente, mesmo quando o código esquece de validar?

O Supabase entrega um Postgres completo, e a API só é tão confiável quanto as tabelas por baixo dela. Chave primária, chave estrangeira, NOT NULL e CHECK fazem o banco recusar dado errado na origem, e o índice certo mantém a consulta rápida quando a tabela cresce.

  • 📄 Tables and data — Supabase Docs Como criar tabelas pelo painel ou por SQL e quais tipos de dado usar.
  • 📄 Table Basics — PostgreSQL CREATE TABLE, colunas e tipos, direto da documentação oficial do Postgres.
  • 📄 Constraints — PostgreSQL NOT NULL, CHECK, UNIQUE, chave primária e chave estrangeira com ON DELETE.
  • 📄 Foreign Keys (tutorial) — PostgreSQL O exemplo curto de integridade referencial entre duas tabelas.

Siga os 10 passos abaixo para construir a prática aplicando os conceitos do bloco:

  1. Configuração do Ambiente: crie um projeto no plano gratuito do Supabase e abra o SQL Editor no painel.
  2. Tabela Pai: crie projetos com id bigint generated always as identity primary key e nome text not null unique.
  3. Tabela Filha: crie tarefas com projeto_id bigint not null references projetos(id) on delete cascade.
  4. Regra no Banco: acrescente ao título check (char_length(trim(titulo)) > 0) — a mesma regra da entidade, agora também no banco.
  5. Datas Automáticas: adicione criada_em timestamptz not null default now().
  6. Dados de Exemplo: insira dois projetos e quatro tarefas com insert into ... values.
  7. Erro Provocado: tente inserir uma tarefa com projeto_id = 999 e leia a mensagem de violação de chave estrangeira; depois tente um título só com espaços e leia a violação do CHECK.
  8. Consulta com Junção: rode select t.titulo, p.nome from tarefas t join projetos p on p.id = t.projeto_id.
  9. Índice na Chave Estrangeira: crie create index tarefas_projeto_id_idx on tarefas (projeto_id) e anote por que a coluna mais usada em filtro merece índice.
  10. Validação e Testes: apague um projeto, confirme que as tarefas dele sumiram pelo cascade e salve todo o script em db/schema.sql no repositório.
Concluiu todos os passos?

🔗 2. Repositório Supabase na API Node

🎯 Desafio

A API da Fala Fácil perde todas as tarefas a cada reinício do servidor, porque o repositório ainda é um array em memória. A arquitetura da aula 23 prometeu que trocar o armazenamento não mexeria no núcleo. Como cumprir essa promessa ligando a API ao Supabase?

O cliente supabase-js conversa com o banco pela API que o Supabase gera a partir das tabelas. Encapsulado num repositório com o mesmo contrato do adaptador em memória, ele entra na borda do sistema sem que os casos de uso percebam a troca.

  • 📄 @supabase/supabase-js — npm Instalação e criação do cliente com URL e chave do projeto.
  • 📄 JavaScript API Reference — Supabase select, insert, filtros como eq e modificadores como single e order.
  • 📄 Joins e tabelas aninhadas — Supabase Como trazer dados de tabelas relacionadas numa única chamada.
  • 📄 Joins Between Tables — PostgreSQL O JOIN em SQL puro, para entender o que o cliente faz por baixo.

Siga os 10 passos abaixo para construir a prática aplicando os conceitos do bloco:

  1. Configuração do Ambiente: instale npm install @supabase/supabase-js e coloque SUPABASE_URL e SUPABASE_SECRET_KEY no .env, copiados de Project Settings → API Keys.
  2. Cliente Único: crie src/infra/db/supabase.js que chama createClient uma vez e exporta a instância.
  3. Esqueleto do Adaptador: crie src/infra/repositories/TarefaSupabaseRepository.js com buscarTodos, buscarPorId e salvar — o mesmo contrato do repositório em memória.
  4. Listagem: implemente supabase.from('tarefas').select('id, titulo, feita').order('id').
  5. Tratando o Retorno: toda chamada devolve { data, error }; se error existir, lance-o para o middleware de erro em vez de devolver data vazio.
  6. Detalhe sem Erro Falso: use .eq('id', id).maybeSingle(): ele devolve null quando não encontra, e o caso de uso decide o 404.
  7. Gravação: implemente .insert({ titulo, feita, projeto_id }).select().single() para receber de volta a linha criada com id.
  8. Erro Provocado: crie uma tarefa com projetoId inexistente, veja o erro do Postgres chegar até a resposta como 500 e decida qual status ele deveria virar.
  9. Junção Embutida: acrescente buscarComProjeto usando select('id, titulo, projetos(nome)') e observe o objeto aninhado no resultado.
  10. Validação e Testes: troque só a linha de instanciação no server.js, reinicie a API e confirme que as tarefas continuam lá; confirme também que os testes da aula 24 seguem passando com o repositório em memória.

🔐 3. Row Level Security e o Uso Correto das Chaves

🎯 Desafio

Um estagiário da Fala Fácil colou a chave secreta do Supabase no JavaScript do site para testar rapidinho. Qualquer visitante que abre o DevTools consegue ler e apagar as tarefas de todos os professores. Como garantir que, mesmo com a chave pública no navegador, cada professor só enxergue o que é dele?

No Supabase, a chave publicável (a antiga anon) pode ir para o navegador; a chave secreta (a antiga service_role) ignora qualquer política e só vive no servidor. Row Level Security é o recurso do Postgres que filtra linha por linha conforme quem pergunta, e é ele que torna a chave pública segura.

  • 📄 Row Level Security — Supabase Docs Como ligar o RLS e escrever políticas com auth.uid().
  • 📄 API keys — Supabase Docs A diferença entre chave publicável e chave secreta e onde cada uma pode estar.
  • 📄 Securing your API — Supabase Docs O que fica exposto pela API automática e como fechar.
  • 📄 RLS Simplified — Supabase Docs Exemplos curtos de políticas para os casos mais comuns.

Siga os 10 passos abaixo para construir a prática aplicando os conceitos do bloco:

  1. Configuração do Ambiente: no SQL Editor, adicione a coluna dono_id uuid references auth.users(id) à tabela tarefas.
  2. Diagnóstico Inicial: com o RLS desligado, consulte a tabela com a chave publicável usando curl "$SUPABASE_URL/rest/v1/tarefas?select=*" -H "apikey: $SUPABASE_PUBLISHABLE_KEY" e veja todas as linhas.
  3. Ligando o RLS: rode alter table tarefas enable row level security e repita a consulta.
  4. Lendo o Resultado: registre por que a resposta virou lista vazia: sem nenhuma política, o RLS nega tudo por padrão.
  5. Política de Leitura: crie create policy "dono le as suas" on tarefas for select to authenticated using ((select auth.uid()) = dono_id).
  6. Política de Escrita: crie a política de insert com with check ((select auth.uid()) = dono_id).
  7. Usuários de Teste: crie dois usuários em Authentication → Users e, num script com a chave publicável, faça signInWithPassword com cada um.
  8. Erro Provocado: logado como o usuário A, tente inserir uma tarefa com o dono_id do usuário B e leia a mensagem de violação de política.
  9. Chave Secreta no Lugar Certo: confirme que a API Node lê a chave secreta só do .env e que ela não aparece em nenhum arquivo servido ao navegador.
  10. Validação e Testes: logado como A, liste e veja só as tarefas de A; repita como B; registre no README qual chave vive em qual lado e por que a chave secreta ignora o RLS.
Concluiu todos os passos?
