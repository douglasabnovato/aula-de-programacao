🌐 1. CORS em Profundidade: Preflight, Credenciais e Lista de Origens

🎯 Desafio

A agência fictícia Trilha Tur tem o site principal, o painel administrativo e um ambiente de homologação, cada um num endereço. A API liberava uma origem só; alguém trocou para o curinga * para resolver, e o login por cookie parou de funcionar de vez. Como liberar exatamente as origens certas, com cookie, sem abrir para o mundo?

Na aula 22 o CORS liberou uma origem fixa. Aplicação real tem várias origens por ambiente, requisições que disparam preflight OPTIONS e cookies que exigem credenciais — e o navegador recusa o curinga quando há credenciais. CORS é regra do navegador: ele protege o usuário, não substitui autenticação.

  • 📄 Cross-Origin Resource Sharing — MDN O guia completo: requisições simples, preflight e requisições com credenciais.
  • 📄 Preflight request — MDN A requisição OPTIONS que o navegador faz antes da real, e quando ela acontece.
  • 📄 Access-Control-Allow-Credentials — MDN Por que credenciais e curinga não andam juntos.
  • 📄 cors middleware — Express As opções origin como função, credentials, methods, allowedHeaders e maxAge.

Siga os 10 passos abaixo para construir a prática aplicando os conceitos do bloco:

  1. Configuração do Ambiente: no .env, crie ORIGENS_PERMITIDAS=http://localhost:5500,http://localhost:5173 e leia a lista separando por vírgula.
  2. Origem Dinâmica: passe origin como função que consulta a lista e chama callback(null, true) só para origens conhecidas.
  3. Observando o Preflight: faça um fetch com método PATCH e Content-Type: application/json e encontre na aba Rede a requisição OPTIONS antes da real.
  4. Métodos e Cabeçalhos: declare methods e allowedHeaders explicitamente, só com o que a API usa.
  5. Credenciais: ligue credentials: true no servidor e credentials: 'include' no fetch.
  6. Erro Provocado: com credenciais ligadas, troque a origem para '*', repita a chamada e leia no console o bloqueio do navegador; volte a lista.
  7. Cookie de Sessão: emita o cookie de sessão com httpOnly, secure e sameSite definidos conforme o ambiente.
  8. Cache do Preflight: configure maxAge: 600 e observe que o OPTIONS some das chamadas seguintes.
  9. Origem Estranha: chame de uma porta fora da lista e confirme que a resposta não traz Access-Control-Allow-Origin.
  10. Validação e Testes: teste as origens do .env e uma desconhecida, faça a mesma chamada com curl e registre no README por que o curl passa: CORS não protege contra cliente fora do navegador.

🚦 2. Rate Limiting em Camadas e por Identidade

🎯 Desafio

A API da Trilha Tur tem limite de 100 requisições por IP, mas todos os funcionários da agência saem pelo mesmo IP e ficam bloqueados às 10h. Enquanto isso, um robô com mil IPs consulta preços de pacotes sem esbarrar em limite nenhum. Como limitar de forma justa, por quem está chamando e pelo custo de cada rota?

Limite por IP é o ponto de partida, não o fim. APIs reais combinam um teto global, limites menores em rotas caras ou sensíveis e contagem por usuário autenticado, e avisam o cliente, pelos cabeçalhos, quanto resta e quando tentar de novo.

  • 📄 express-rate-limit — repositório oficial windowMs, limit, keyGenerator, standardHeaders, handler e stores.
  • 📄 429 Too Many Requests — MDN O status que diz ao cliente que ele passou do limite.
  • 📄 Retry-After — MDN O cabeçalho que informa quanto tempo esperar antes de tentar de novo.
  • 📄 API4:2023 Unrestricted Resource Consumption — OWASP O risco que o rate limiting combate e os outros limites que o acompanham.

Siga os 10 passos abaixo para construir a prática aplicando os conceitos do bloco:

  1. Configuração do Ambiente: no projeto que já tem o express-rate-limit da aula 22, crie src/middlewares/limites.js.
  2. Camada Global: crie um limitador de 300 requisições a cada 15 minutos por IP para toda a API, com standardHeaders: 'draft-8'.
  3. Lendo os Cabeçalhos: faça chamadas e observe os cabeçalhos RateLimit e RateLimit-Policy na resposta.
  4. Rota Cara: aplique um limite menor, 20 por minuto, só em /relatorios.
  5. Por Identidade: depois do middleware de JWT, crie um limitador com keyGenerator que usa req.usuarioId e cai para ipKeyGenerator(req.ip) quando não há usuário.
  6. Erro Provocado: registre por engano o limitador de relatórios com app.use global, faça 21 chamadas a /tarefas e veja o bloqueio indevido; volte-o para a rota certa.
  7. Resposta 429 Útil: escreva um handler que devolve Problem Details com o tempo de espera, coerente com o Retry-After.
  8. Login mais Rígido: no limitador de login, use skipSuccessfulRequests: true para contar só as tentativas que falharam.
  9. Várias Instâncias: registre no README que o armazenamento padrão é em memória — com duas instâncias da API, cada uma conta sozinha — e que um store compartilhado resolveria.
  10. Validação e Testes: rode um script que dispara 30 chamadas seguidas e conta os status recebidos; confira o comportamento de cada camada.
Concluiu todos os passos?

🔍 3. Auditoria de Segurança: Segredos, Dependências e Cabeçalhos

🎯 Desafio

Antes de colocar a API da Trilha Tur no ar, o cliente pediu respostas simples: há biblioteca com falha conhecida? Algum segredo está no repositório? A API sobe se faltar uma variável de ambiente? Ninguém no time sabe responder com certeza. Como transformar essas perguntas numa checagem que roda sempre, e não só quando alguém lembra?

Segurança não termina no código da rota. Dependências herdam falhas de terceiros, segredos vazam por commit e variável faltando vira erro em produção na primeira requisição. Uma auditoria repetível junta npm audit, validação das variáveis na subida da API, revisão do log e cabeçalhos de resposta ajustados.

  • 📄 Auditing package dependencies — npm Docs Como ler o relatório do npm audit e o que o audit fix faz.
  • 📄 Secrets Management Cheat Sheet — OWASP Onde guardar, como rotacionar e o que fazer quando um segredo vaza.
  • 📄 HTTP Headers Cheat Sheet — OWASP Quais cabeçalhos de resposta ligar, quais remover e por quê.
  • 📄 Content Security Policy — MDN O cabeçalho que restringe de onde a página pode carregar recursos.

Siga os 10 passos abaixo para construir a prática aplicando os conceitos do bloco:

  1. Configuração do Ambiente: rode npm audit no projeto e leia a gravidade e o caminho de dependência de cada item.
  2. Corrigindo sem Quebrar: rode npm audit fix sem --force e anote o que exigiria versão maior de alguma biblioteca.
  3. Script de Auditoria: adicione "audit:prod": "npm audit --omit=dev --audit-level=high" em scripts.
  4. Validando o Ambiente: crie src/config/env.js que valida com Zod PORT, JWT_SECRET com pelo menos 32 caracteres, SUPABASE_URL e ORIGENS_PERMITIDAS.
  5. Erro Provocado: apague JWT_SECRET do .env, suba a API e confirme que ela se recusa a iniciar com mensagem clara, em vez de falhar no primeiro login.
  6. Procurando Segredos: rode git log -p | grep -i -E "secret|senha|api_key" e, se algo aparecer, rotacione a chave no provedor — apagar o commit não basta.
  7. Modelo de Ambiente: versione um .env.example com as chaves sem valores, no lugar do .env.
  8. CSP para API: como a API só devolve JSON, configure no helmet defaultSrc: ["'none'"] e frameAncestors: ["'none'"] e compare o cabeçalho antes e depois.
  9. Log sem Segredo: revise o log estruturado da aula 26 e garanta que authorization, senha e token nunca são impressos.
  10. Validação e Testes: crie npm run seguranca que roda audit:prod e a checagem de ambiente; registre no README o resultado e a data da auditoria.
Concluiu todos os passos?
