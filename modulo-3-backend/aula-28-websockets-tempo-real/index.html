🔄 1. Do Polling ao WebSocket

🎯 Desafio

O painel de pedidos da lanchonete fictícia Sabor da Praça pergunta ao servidor a cada dois segundos se chegou pedido novo. Com trinta tablets ligados, são novecentas requisições por minuto, e quase todas respondem que não há nada novo. Como o servidor avisa o tablet no momento em que o pedido chega, sem ser perguntado?

HTTP é pergunta e resposta: o servidor só fala quando o cliente pede. O WebSocket começa como uma requisição HTTP, pede um upgrade e mantém um canal aberto nos dois sentidos, por onde qualquer lado envia mensagens a qualquer momento.

  • 📄 Escrevendo aplicações cliente WebSocket — MDN O objeto WebSocket do navegador: abrir, enviar, receber e fechar.
  • 📄 Escrevendo um servidor WebSocket — MDN O handshake e o formato das mensagens do lado do servidor.
  • 📄 RFC 6455 — The WebSocket Protocol A especificação do protocolo, com o upgrade e o status 101.
  • 📄 ws — repositório oficial A biblioteca de WebSocket para Node usada nesta prática.

Siga os 10 passos abaixo para construir a prática aplicando os conceitos do bloco:

  1. Configuração do Ambiente: crie a pasta painel-ws, rode npm init -y e npm install ws.
  2. Servidor: em servidor-ws.js, crie new WebSocketServer({ port: 8080 }).
  3. Conexão: escute o evento connection e envie uma mensagem de boas-vindas com socket.send.
  4. Cliente no Navegador: crie cliente.html com new WebSocket('ws://localhost:8080') e um onmessage que escreve na tela.
  5. Observando o Handshake: abra a aba Rede, filtre por WS e encontre o status 101 Switching Protocols e as mensagens trocadas.
  6. Mensagens Estruturadas: envie JSON com tipo e dados e faça JSON.parse do outro lado.
  7. Difusão: ao receber um pedido, percorra wss.clients e envie para cada um com readyState === WebSocket.OPEN.
  8. Erro Provocado: mande do cliente um texto que não é JSON, veja o servidor cair no JSON.parse e proteja com try/catch devolvendo uma mensagem de erro só para quem enviou.
  9. Desconexão: escute close e imprima quantos clientes continuam conectados.
  10. Validação e Testes: abra três abas, envie um pedido de uma e confirme que as três recebem; registre no README a comparação de número de requisições com o polling.

📡 2. Socket.IO: Eventos, Difusão e Salas

🎯 Desafio

A Sabor da Praça abriu uma segunda unidade, e agora a cozinha do Centro recebe no painel os pedidos do bairro São Pedro. Além disso, quando o Wi-Fi oscila, o tablet perde a conexão e não volta sozinho. Como separar as mensagens por unidade e reconectar sem ninguém recarregar a página?

Socket.IO é uma camada sobre o WebSocket que acrescenta eventos com nome, confirmação de recebimento, reconexão automática e salas. Sala é um grupo de conexões no servidor: emitir para a sala centro alcança só quem entrou nela.

  • 📄 Introdução — Socket.IO O que o Socket.IO acrescenta ao WebSocket e o que ele não é.
  • 📄 Tutorial oficial — Socket.IO O passo a passo de um chat com Express, do servidor ao cliente.
  • 📄 Rooms — Socket.IO join, leave e emissão para uma sala específica.
  • 📄 Broadcasting — Socket.IO Emitir para todos, para todos menos um e para um grupo.

Siga os 10 passos abaixo para construir a prática aplicando os conceitos do bloco:

  1. Configuração do Ambiente: crie o projeto painel-pedidos e instale npm install express socket.io.
  2. Servidor Compartilhado: crie o servidor com http.createServer(app) e passe-o para new Server(servidor): REST e tempo real na mesma porta.
  3. Cliente: sirva public/painel.html carregando /socket.io/socket.io.js, entregue pelo próprio servidor.
  4. Evento com Nome: no cliente, emita entrar-unidade com o nome da unidade escolhida.
  5. Entrando na Sala: no servidor, trate o evento com socket.join(unidade).
  6. Pedido pela API REST: crie POST /pedidos que guarda o pedido e chama io.to(pedido.unidade).emit('pedido-novo', pedido).
  7. Erro Provocado: troque io.to(pedido.unidade).emit por io.emit e veja o pedido aparecer nas duas cozinhas; volte a versão com sala.
  8. Confirmação de Recebimento: no evento pedido-pronto, use o callback de confirmação para o tablet saber que o servidor registrou.
  9. Reconexão: derrube o servidor, suba de novo e observe o cliente reconectar sozinho; emita entrar-unidade de novo dentro do evento connect.
  10. Validação e Testes: abra um painel por unidade, crie pedidos pelo Insomnia e confirme que cada um chega só na unidade certa; registre no README o fluxo REST para tempo real.

🔏 3. Autenticação e Limites na Conexão em Tempo Real

🎯 Desafio

Qualquer pessoa que descobrir o endereço do servidor da Sabor da Praça consegue abrir uma conexão, entrar na sala de qualquer unidade e ler os pedidos com o endereço dos clientes. A API REST exige token desde a aula 22, mas o canal em tempo real ficou aberto. Como aplicar a mesma regra de acesso na conexão?

A conexão é autenticada uma vez, no handshake, e a identidade vale enquanto ela estiver aberta. No Socket.IO isso é feito com um middleware io.use que lê o token enviado em auth, verifica o JWT e guarda o usuário para decidir a quais salas ele pode entrar.

  • 📄 Middlewares — Socket.IO Como rodar código antes de aceitar a conexão e recusar com erro.
  • 📄 Introdução ao JWT — jwt.io A estrutura do token verificado no handshake, o mesmo da aula 22.
  • 📄 Handling disconnections — Socket.IO O que acontece com eventos enviados enquanto o cliente está desconectado.
  • 📄 Connection state recovery — Socket.IO Recuperar salas e mensagens perdidas numa queda curta de conexão.
🎥 Vídeos de apoio
  • ▶️ #20 - Criando um Middleware de validação de token JWT | MERN STACK Thiago Veigah · 32:21 — Cria um middleware de validação de token JWT, o mesmo mecanismo usado para autenticar a conexão no handshake.

Siga os 10 passos abaixo para construir a prática aplicando os conceitos do bloco:

  1. Configuração do Ambiente: no projeto da prática anterior, instale npm install jsonwebtoken dotenv e reutilize o JWT_SECRET da aula 22 no .env.
  2. Token no Cliente: conecte com io({ auth: { token } }) — o token vai no corpo do handshake, nunca na query string da URL.
  3. Middleware de Conexão: registre io.use((socket, proximo) => { ... }) lendo socket.handshake.auth.token.
  4. Verificação: use jwt.verify; na falha, chame proximo(new Error('nao autorizado')).
  5. Erro Provocado: conecte sem token e trate connect_error no cliente, mostrando a mensagem na tela em vez de ficar tentando para sempre.
  6. Dados do Usuário: guarde o payload decodificado em socket.data.usuario.
  7. Autorização por Sala: no entrar-unidade, só aceite a entrada se a unidade estiver em socket.data.usuario.unidades.
  8. Validando Mensagens: recuse, com resposta pelo callback, eventos cujo payload não tenha os campos esperados com o tipo certo.
  9. Limite de Eventos: conte eventos por conexão numa janela de 10 segundos e desconecte quem passar de 20.
  10. Validação e Testes: teste sem token, com token de outra unidade e com token certo; registre no README o que cada caso recebeu.
Concluiu todos os passos?
