Caça à Abstração que Não se Pagou

Aula 62 · Módulo 7: Avançado (Engenharia e Arquitetura Master) · ByteClass

O erro previsível de quem acabou de estudar padrões

Ver padrão em tudo. Uma interface por classe, uma fábrica por objeto, um evento por chamada. O código fica "bonito" segundo o livro e insuportável de seguir.

Os três sinais de excesso

1. Interface com uma implementação só, sem previsão de segunda

interface RepositorioDeUsuario { ... }
class RepositorioDeUsuarioPostgres implements RepositorioDeUsuario { ... }
// ... e nada mais, há dois anos

A interface custa um arquivo e uma indireção. Se não há segunda implementação nem intenção de ter uma, e o teste usa o banco de verdade, ela não se pagou.

2. Método que só repassa

class ServicoDeUsuario {
  constructor(repo) { this.repo = repo; }
  buscarPorId(id) { return this.repo.buscarPorId(id); }   // não decide nada
  listar()        { return this.repo.listar(); }          // idem
}

Essa camada não acrescenta comportamento — acrescenta um arquivo a abrir.

3. Seis arquivos para achar um if

rota → controlador → caso de uso → serviço → repositório → adaptador
                                                          ↑
                                              o if está aqui

Acima de quatro saltos para encontrar a lógica, o custo de manutenção já superou o de organização.

A regra dos três

1ª vezescreva direto
2ª vezduplique e incomode-se
3ª vezagora abstraia — você já conhece as três variações

Abstrair na primeira é chute sobre o futuro. Na terceira, é generalização baseada em evidência — e costuma ser uma abstração melhor, porque nasce do caso real e não da imaginação.

Ficha de auditoria

Interface / contrato: ___
  Implementações reais hoje:        ___
  Há previsão concreta de outra?    ( ) sim, qual: ___  ( ) não
  O teste usa um dublê dela?        ( ) sim  ( ) não
  Arquivos entre a chamada e a lógica: ___

  Veredito:  ( ) mantém  ( ) funde com a vizinha  ( ) remove

Como remover com segurança

  1. Confirme que os testes passam antes de tocar em qualquer coisa.
  2. Remova a abstração e ligue o chamador direto à implementação.
  3. Rode os testes. Se passarem, a abstração não estava sustentando nada.
  4. Escreva um ADR registrando a remoção — inclusive para saber que já foi tentado.
