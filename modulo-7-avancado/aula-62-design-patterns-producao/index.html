🏭 1. Padrões de Criação: Factory, Builder e Singleton

Os três resolvem a mesma pergunta por caminhos diferentes: como criar um objeto sem espalhar a decisão de construção por todo o código.

  • 📄 Padrões Criacionais — Refactoring Guru (PT-BR) Cada padrão com problema, solução, diagrama e exemplo em várias linguagens.
  • 📄 Factory Method — Refactoring Guru Quando usar, quando não usar, e a diferença para Abstract Factory.
  • 📄 Singleton — Refactoring Guru Inclui a seção honesta sobre por que muita gente o considera um antipadrão.
  • 📄 Módulos JavaScript — MDN Por que em JS o módulo já resolve boa parte do que o Singleton resolveria.

🎥 Curadoria de vídeo pendente. Este bloco recebe os vídeos de apoio selecionados pelo instrutor para o tema acima.

Siga os 10 passos abaixo para construir a prática aplicando os conceitos do bloco:

  1. Configuração do Ambiente: abra a API dos módulos anteriores e localize onde objetos são criados.
  2. Buscando o Problema: encontre um if que escolhe entre implementações diferentes.
  3. Criando a Factory: extraia essa escolha para uma função que devolve a implementação certa.
  4. Simplificando o Chamador: confirme que quem usa não sabe mais qual implementação veio.
  5. Buscando o Construtor Grande: encontre um objeto criado com mais de cinco parâmetros.
  6. Criando o Builder: escreva uma classe com métodos encadeáveis que monta o objeto por partes.
  7. Validando na Construção: no método final, verifique se os campos obrigatórios foram preenchidos.
  8. Avaliando o Singleton: encontre um recurso que deveria ser único e teste se um módulo já resolve.
  9. Registrando a Decisão: escreva um ADR curto para cada padrão aplicado, com o custo aceito.
  10. Validação e Testes: confirme que o comportamento externo não mudou — padrão é refatoração, não recurso novo.
Concluiu todos os passos?

🔧 2. Padrões Estruturais e Comportamentais no Dia a Dia

Adapter, Strategy e Observer são os que mais aparecem em código JavaScript real — muitas vezes sem que a pessoa saiba que está usando um padrão nomeado.

  • 📄 Padrões Estruturais — Refactoring Guru Adapter, Decorator, Facade e Proxy, com exemplos aplicados.
  • 📄 Padrões Comportamentais — Refactoring Guru Strategy, Observer, Command e os demais padrões de interação entre objetos.
  • 📄 Strategy — Refactoring Guru O padrão que substitui condicional grande por objetos intercambiáveis.
  • 📄 addEventListener — MDN O Observer embutido na plataforma web, que todo dev usa desde o primeiro dia.

🎥 Curadoria de vídeo pendente. Este bloco recebe os vídeos de apoio selecionados pelo instrutor para o tema acima.

Siga os 10 passos abaixo para construir a prática aplicando os conceitos do bloco:

  1. Configuração do Ambiente: localize no seu código um switch ou cadeia de if com quatro ou mais ramos.
  2. Documentando o Antes: conte as linhas do bloco e anote quantas razões ele tem para mudar.
  3. Extraindo a Primeira Estratégia: mova um ramo para uma função ou classe com nome próprio.
  4. Definindo o Contrato: garanta que todas as estratégias recebem e devolvem a mesma coisa.
  5. Extraindo as Demais: repita para cada ramo restante, sem alterar comportamento.
  6. Criando o Mapa: substitua o switch por um objeto que liga a chave à estratégia.
  7. Tratando o Padrão: defina o que acontece quando a chave não existe no mapa.
  8. Testando Isoladamente: escreva um teste para cada estratégia, separadamente.
  9. Acrescentando uma Nova: adicione uma quinta estratégia e verifique que nada mais precisou mudar.
  10. Validação e Testes: compare o antes e o depois e registre quantas linhas mudaram para acrescentar a quinta.

🚫 3. O Excesso: Quando o Padrão Piora o Código

Quem acabou de estudar padrões vê padrão em tudo. O bloco fecha com o critério oposto: como reconhecer a abstração que não se pagou e como desfazê-la.

  • 📄 YAGNI — Martin Fowler O argumento contra construir a abstração antes de ter a necessidade.
  • 📄 Code Smells — Refactoring Guru O catálogo de sinais de problema, incluindo os de excesso de abstração.
  • 📄 Dívida Técnica — Martin Fowler Por que abstração desnecessária também é dívida, só que menos visível.
  • 📄 Google — o padrão do revisor O critério de aprovar o que melhora o sistema, sem exigir perfeição.

Siga os 10 passos abaixo para construir a prática aplicando os conceitos do bloco:

  1. Configuração do Ambiente: escolha o projeto mais estruturado que você tem.
  2. Listando as Interfaces: liste todo contrato, classe abstrata ou porta declarada.
  3. Contando Implementações: para cada um, conte quantas implementações reais existem.
  4. Marcando as Solitárias: separe as que têm exatamente uma e nunca tiveram outra.
  5. Checando a Previsão: para cada solitária, verifique se há previsão concreta de uma segunda.
  6. Medindo a Indireção: escolha um comportamento e conte os arquivos até achar a implementação.
  7. Buscando o Repasse: marque métodos que só chamam outro método sem decidir nada.
  8. Propondo a Remoção: escolha a abstração menos justificada e escreva como seria sem ela.
  9. Executando a Remoção: remova uma delas e rode os testes.
  10. Validação e Testes: compare a contagem de arquivos e linhas antes e depois, e registre o resultado.
Concluiu todos os passos?
