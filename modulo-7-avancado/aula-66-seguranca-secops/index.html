🗺️ 1. Modelagem de Ameaças: Pensar como Quem Ataca

🎯 Desafio

A startup fictícia Consulta Já vai lançar um aplicativo em que pacientes enviam exames para médicos parceiros. O time já configurou HTTPS, CORS e rate limiting, e acha que isso basta. Antes do lançamento, quais caminhos um atacante usaria para ler o exame de outra pessoa, e como descobrir isso no papel antes de descobrir em produção?

Modelagem de ameaças é o exercício de desenhar o sistema, marcar onde os dados cruzam fronteiras de confiança e perguntar, em cada ponto, o que pode dar errado. Feita antes do código, ela transforma segurança de lista genérica em riscos específicos, priorizados e com dono. A aula 29 tratou das defesas de borda; aqui o olhar vai para o sistema inteiro.

  • 📄 Threat Modeling Cheat Sheet — OWASP As quatro perguntas da modelagem de ameaças, o uso do STRIDE e como registrar os resultados.
  • 📄 Attack Surface Analysis Cheat Sheet — OWASP Como inventariar todos os pontos de entrada do sistema e medir quando a superfície cresce.
  • 📄 OWASP Top Ten As categorias de risco mais comuns em aplicações web, usadas como lista de verificação do modelo.
  • 📄 Application Security Verification Standard — OWASP Requisitos verificáveis de segurança, por nível, para transformar cada ameaça em critério de aceite.

  • ▶️ Treinamento Starter - Aula 03 - Modelagem de Ameaças Conviso Application Security · 8:28 — Aula introdutória sobre modelagem de ameaças e como identificar riscos em cada parte do sistema.

Siga os 10 passos abaixo para construir a prática aplicando os conceitos do bloco:

  1. Configuração do Ambiente: crie docs/seguranca/modelo-de-ameacas.md no projeto final do Módulo 4.
  2. Desenhando o Fluxo: faça o diagrama de fluxo de dados: usuário, frontend, API, banco, armazenamento de arquivos e serviços externos.
  3. Marcando as Fronteiras: trace as fronteiras de confiança, como internet para API e API para banco, e numere cada fluxo que cruza uma delas.
  4. Inventário da Superfície: liste todas as rotas públicas, uploads, webhooks e painéis administrativos com o tipo de autenticação de cada um.
  5. Aplicando STRIDE: para cada fluxo que cruza fronteira, escreva uma ameaça por letra aplicável: falsificação, adulteração, repúdio, vazamento, negação de serviço e elevação de privilégio.
  6. Erro de Escopo: tente listar ameaças sem o diagrama e compare com a lista feita a partir dele; anote quantas ficaram de fora na primeira tentativa.
  7. Pontuando o Risco: dê nota de 1 a 3 para probabilidade e impacto e ordene as ameaças pelo produto.
  8. Definindo a Mitigação: para as cinco primeiras, escreva a defesa, o requisito ASVS correspondente e quem é responsável.
  9. Convertendo em Trabalho: transforme cada mitigação em issue com critério de aceite verificável.
  10. Validação e Testes: apresente o modelo a um colega que fará o papel de atacante e registre no documento as ameaças novas que ele encontrar.
Concluiu todos os passos?

🗡️ 2. Ofensiva Controlada: Explorando e Corrigindo IDOR e Injeção

🎯 Desafio

A plataforma fictícia Nota Certa, de emissão de notas fiscais para microempresas, tem uma rota GET /notas/:id que confere se o usuário está logado. Um cliente percebeu que, trocando o número na URL, consegue baixar a nota de outra empresa, e a busca por nome ainda monta o SQL concatenando texto. Como reproduzir o ataque num ambiente de laboratório, provar a falha e corrigir de forma que ela não volte?

Segurança ofensiva, feita com autorização e em ambiente próprio, é a forma mais direta de entender por que uma defesa existe. Controle de acesso quebrado (IDOR) e injeção de SQL continuam entre os riscos mais comuns: o primeiro nasce de confundir autenticação com autorização; o segundo, de misturar dado com comando.

  • 📄 A01:2021 Broken Access Control — OWASP Top 10 A categoria que inclui IDOR, com cenários de ataque e formas de prevenção.
  • 📄 Authorization Cheat Sheet — OWASP Como verificar a permissão em cada requisição, negando por padrão.
  • 📄 SQL Injection Prevention Cheat Sheet — OWASP Consultas parametrizadas como defesa principal e o que fazer quando não é possível usá-las.
  • 📄 Testing for SQL Injection — OWASP WSTG O roteiro de teste usado por profissionais para confirmar uma injeção de SQL.

Siga os 10 passos abaixo para construir a prática aplicando os conceitos do bloco:

  1. Configuração do Ambiente: suba a API de laboratório com PostgreSQL em contêiner, crie duas empresas e três notas para cada uma. Faça isso só no seu ambiente: atacar sistema de terceiros sem autorização é crime.
  2. Mapeando o Alvo: liste as rotas que recebem identificador na URL ou texto livre de busca.
  3. Explorando o IDOR: faça login como a empresa A e peça GET /notas/4, que pertence à empresa B; registre a resposta 200 com os dados alheios.
  4. Explorando a Injeção: na busca, envie ' OR '1'='1 como nome e observe a lista trazer notas de todas as empresas.
  5. Escrevendo o Teste que Falha: antes de corrigir, escreva dois testes automatizados que reproduzem os ataques e confirme que eles passam contra o código vulnerável, provando a falha.
  6. Corrigindo a Autorização: inclua empresa_id da sessão no WHERE da consulta e responda 404 quando a nota não pertence ao usuário.
  7. Corrigindo a Injeção: troque a concatenação por consulta parametrizada com $1 e passe o termo no array de valores.
  8. Invertendo os Testes: ajuste os testes para esperar 404 no IDOR e lista vazia na injeção, e confirme que agora passam.
  9. Buscando Irmãos: procure no resto do código com grep por req.params.id sem filtro de dono e por consultas montadas com template string.
  10. Validação e Testes: rode a suíte completa, registre no README o antes e depois de cada ataque e a regra de revisão que impede a falha de voltar.
Concluiu todos os passos?

🔐 3. DevSecOps: Segurança Automatizada no Pipeline

🎯 Desafio

Na agência fictícia Pixel Norte, uma chave de API de pagamento foi parar num commit público e só foi descoberta quando a conta recebeu cobranças estranhas. No mesmo mês, uma biblioteca antiga com vulnerabilidade conhecida seguiu em produção por semanas. Como fazer o pipeline encontrar segredos e dependências vulneráveis antes do merge, sem depender da memória de ninguém?

DevSecOps é colocar verificações de segurança no mesmo fluxo automatizado que já roda testes e deploy. Varredura de segredos, auditoria de dependências, análise estática de segurança e atualização automática de pacotes funcionam como camadas: cada uma pega o que a outra deixa passar, e todas rodam em cada pull request.

  • 📄 CI/CD Security Cheat Sheet — OWASP Os riscos do próprio pipeline e as verificações que ele deve executar.
  • 📄 Secrets Management Cheat Sheet — OWASP Onde guardar segredos, como rotacioná-los e o que fazer quando um vaza.
  • 📄 Vulnerable Dependency Management Cheat Sheet — OWASP Como decidir entre atualizar, mitigar ou aceitar o risco de uma dependência vulnerável.
  • 📄 npm audit — documentação do npm O comando que compara as dependências instaladas com o banco de vulnerabilidades conhecidas.

Siga os 10 passos abaixo para construir a prática aplicando os conceitos do bloco:

  1. Configuração do Ambiente: no repositório do projeto, crie .github/workflows/secops.yml e .github/dependabot.yml.
  2. Segredo Plantado: numa branch de teste, crie um arquivo com uma chave falsa no formato de token conhecido e faça commit, para ter o que detectar.
  3. Varredura de Segredos: adicione o job de gitleaks com fetch-depth: 0, para varrer o histórico inteiro, e confirme que ele falha apontando o commit.
  4. Corrigindo o Vazamento: remova o arquivo, mova o valor para process.env e escreva no README por que apagar o arquivo não basta: a chave real precisaria ser revogada.
  5. Auditoria de Dependências: adicione npm audit --audit-level=high e instale de propósito uma versão antiga de pacote com vulnerabilidade conhecida para ver o job falhar.
  6. Análise Estática de Segurança: adicione o CodeQL para JavaScript e aguarde o primeiro resultado na aba de segurança do repositório.
  7. Atualização Automática: configure o Dependabot para abrir PRs semanais de atualização de pacotes npm e de actions.
  8. Menor Privilégio no Pipeline: declare permissions explícitas em cada job, dando escrita apenas onde o CodeQL precisa publicar resultado.
  9. Tornando Obrigatório: marque os jobs de segredos e de dependências como verificações obrigatórias na proteção da branch.
  10. Validação e Testes: abra um PR limpo e confirme todos os jobs verdes; registre no README o que cada camada detecta e o que nenhuma delas detecta.
Concluiu todos os passos?
