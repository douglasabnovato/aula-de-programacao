# Checklist de Revisão

1. **Design**: a mudança pertence a este módulo? Cria dependência nova entre camadas?
2. **Regra de negócio**: o comportamento bate com a issue? Leia o cálculo, não só a assinatura.
3. **Casos de borda**: valor zero, lista vazia, usuário sem permissão, concorrência.
4. **Testes**: falhariam se o código estivesse errado? Testam comportamento ou implementação?
5. **Complexidade**: alguém do time entenderia isto daqui a seis meses sem o autor?
6. **Nomes**: variáveis e funções dizem o que fazem no vocabulário do negócio?
7. **Estilo**: só o que o lint não pega.

## Prefixos de comentário
- `bloqueante:` precisa mudar antes do merge
- `sugestão:` melhoria opcional, o autor decide
- `dúvida:` pergunta para entender, sem pedido de mudança
<!-- Fim de checklist-de-revisao.md -->

Como rodar

  1. Crie os três arquivos nos caminhos indicados
  2. Troque os nomes de time pelos usuários ou times reais do seu repositório
  3. Abra um PR que altera src/pagamentos/ e confira quem foi marcado
  4. Ative a exigência de aprovação de code owners na proteção da branch

O que observar

  • No CODEOWNERS, a ordem importa: a regra mais específica deve vir depois da genérica.
  • O modelo de PR pede plano de reversão, o que obriga o autor a pensar no risco antes de pedir revisão.
  • O checklist põe estilo por último de propósito: o que a ferramenta mede não deve ocupar o tempo do revisor.
