📏 1. Análise Estática e o Portão de Qualidade

🎯 Desafio

A software house fictícia Trilha Digital herdou o código de um aplicativo de delivery com 40 mil linhas e nenhum padrão. Cada revisão de código vira discussão de estilo, e funções de 300 linhas continuam entrando porque ninguém tem tempo de apontar. Como fazer a máquina barrar o que é mensurável para que a revisão humana cuide do que só uma pessoa enxerga?

Complexidade ciclomática, profundidade de aninhamento, tamanho de função e duplicação podem ser medidos por ferramenta. Quando essas métricas viram regra no lint e condição obrigatória no pipeline (quality gate), a auditoria deixa de ser opinião e passa a ser um número que bloqueia o merge.

  • 📄 Regra complexity — ESLint Como o ESLint calcula a complexidade ciclomática de cada função e como definir o limite.
  • 📄 Understanding quality gates — SonarQube Cloud O conceito de portão de qualidade aplicado só ao código novo, sem exigir que o legado seja zerado.
  • 📄 About protected branches — GitHub Docs Como exigir que as verificações passem antes de permitir o merge na branch principal.
  • 📄 Design Stamina Hypothesis — Martin Fowler Por que investir em qualidade interna acelera a entrega depois de um certo ponto do projeto.

Siga os 10 passos abaixo para construir a prática aplicando os conceitos do bloco:

  1. Configuração do Ambiente: abra a API do projeto final do Módulo 4 e instale npm install -D eslint @eslint/js globals.
  2. Medindo o Ponto de Partida: rode o ESLint com a regra complexity em modo aviso e salve a lista das dez funções mais complexas.
  3. Escolhendo os Limites: defina complexity em 10, max-depth em 3 e max-lines-per-function em 60, anotando no README o motivo de cada número.
  4. Configurando o Lint: crie o eslint.config.js no formato flat com as regras como erro e rode npx eslint src.
  5. Provocando a Reprovação: escreva de propósito uma função com cinco if aninhados e confirme a mensagem de erro com o valor medido.
  6. Separando Novo de Legado: para não travar o time, limite o erro aos arquivos alterados usando git diff --name-only origin/main no script de verificação.
  7. Script de Auditoria: adicione ao package.json o script audit:qualidade que roda lint, testes com cobertura e npm audit --audit-level=high.
  8. Pipeline: crie o workflow .github/workflows/qualidade.yml que roda o script em todo pull request.
  9. Bloqueando o Merge: na proteção da branch main, marque o job de qualidade como verificação obrigatória.
  10. Validação e Testes: abra um PR com a função complexa, confirme o bloqueio, refatore até passar e registre no README as métricas antes e depois.

🔍 2. Code Review Avançado: Critério, Tamanho e Responsáveis

🎯 Desafio

Na fintech fictícia Moeda Clara, pull requests de 2.000 linhas ficam dias parados e voltam aprovados com um único comentário: 'LGTM'. Um desses PRs levou para produção um cálculo de juros errado que ninguém leu de verdade. Como organizar a revisão para que ela encontre problemas de design e de regra de negócio, e não só vírgula fora do lugar?

Uma revisão útil depende de três coisas: PRs pequenos o bastante para serem lidos, um critério explícito do que olhar (design, funcionalidade, complexidade, testes, nomes) e responsáveis definidos por área do código. O Google publica o guia que usa internamente, e o GitHub oferece os mecanismos para colocar isso em prática.

  • 📄 What to look for in a code review — Google A lista ordenada do que o revisor deve examinar, do design aos comentários.
  • 📄 Small CLs — Google Por que mudanças pequenas são revisadas melhor e como quebrar uma mudança grande.
  • 📄 About code owners — GitHub Docs Como o arquivo CODEOWNERS pede revisão automática das pessoas responsáveis por cada pasta.
  • 📄 Creating a pull request template — GitHub Docs Como padronizar a descrição de todo PR com contexto, risco e forma de testar.

Siga os 10 passos abaixo para construir a prática aplicando os conceitos do bloco:

  1. Configuração do Ambiente: escolha um repositório de equipe (ou o da turma) e crie a pasta .github/ na raiz.
  2. Medindo a Situação Atual: levante os últimos dez PRs: linhas alteradas, tempo até a primeira revisão e número de comentários de cada um.
  3. Definindo o Limite de Tamanho: com base nos dados, escolha um teto (por exemplo, 400 linhas) e escreva no CONTRIBUTING.md como dividir o que passar disso.
  4. Modelo de PR: crie .github/pull_request_template.md com as seções contexto, o que mudou, como testar, riscos e checklist.
  5. Responsáveis por Área: crie .github/CODEOWNERS ligando src/pagamentos/ e src/auth/ às pessoas ou times responsáveis.
  6. Critério do Revisor: escreva um checklist de revisão em ordem de prioridade: design, regra de negócio, casos de borda, testes, nomes e só por último estilo.
  7. Classificando Comentários: combine prefixos como bloqueante:, sugestão: e dúvida: para que o autor saiba o que precisa mudar.
  8. Revisão Provocada: abra um PR grande de propósito e peça revisão; depois divida o mesmo conteúdo em três PRs e compare a qualidade dos comentários recebidos.
  9. Exigindo a Revisão: na proteção da branch, exija aprovação de code owners antes do merge.
  10. Validação e Testes: abra um PR que altera src/pagamentos/, confirme que o responsável foi marcado automaticamente e registre no README o antes e depois das métricas.

🔥 3. Hotspots: Onde a Dívida Técnica Custa Mais

🎯 Desafio

A diretoria da empresa fictícia Rota Fácil Logística aprovou duas semanas para 'pagar dívida técnica', e o time não sabe por onde começar: há centenas de arquivos feios. Refatorar um arquivo que ninguém toca há três anos não devolve nada ao negócio. Como escolher, com dados, os poucos arquivos em que a melhoria vai acelerar o trabalho de verdade?

Nem toda dívida técnica cobra juros. O custo aparece onde código complexo encontra mudança frequente: o histórico do Git mostra quais arquivos mudam mais, a análise estática mostra quais são mais complexos, e o cruzamento dos dois aponta os hotspots que justificam o investimento.

  • 📄 git log — documentação oficial do Git As opções de formatação e filtro que transformam o histórico em dado analisável, como --numstat e --since.
  • 📄 Technical Debt Quadrant — Martin Fowler Os quatro tipos de dívida técnica e por que a origem dela muda a forma de tratar.
  • 📄 The Standard of Code Review — Google O critério de aprovar o que melhora a saúde do código, útil para decidir até onde refatorar.
  • 📄 The CL author's guide — Google Como apresentar uma refatoração para revisão sem misturá-la com mudança de comportamento.

Siga os 10 passos abaixo para construir a prática aplicando os conceitos do bloco:

  1. Configuração do Ambiente: clone um repositório com pelo menos um ano de histórico e crie o arquivo scripts/hotspots.js.
  2. Lendo o Histórico: rode git log --since=12.months --numstat --format= e observe as colunas de linhas adicionadas, removidas e o caminho.
  3. Contando Mudanças: no script, agrupe a saída por arquivo e conte quantos commits alteraram cada um.
  4. Medindo Tamanho: para cada arquivo, conte as linhas atuais como aproximação de complexidade.
  5. Erro Provocado: rode o script sem filtrar arquivos gerados e observe package-lock.json no topo; ajuste o filtro para ignorar lockfiles e pastas de build.
  6. Calculando o Hotspot: multiplique mudanças por tamanho normalizado e ordene do maior para o menor.
  7. Cruzando com o Lint: para os cinco primeiros, rode o ESLint com a regra complexity e anote a função mais complexa de cada um.
  8. Classificando a Dívida: encaixe cada hotspot num quadrante de Fowler: deliberada ou inadvertida, prudente ou imprudente.
  9. Priorizando: escolha até três arquivos e escreva para cada um: o problema, a refatoração proposta e qual tarefa de negócio ela acelera.
  10. Validação e Testes: apresente a tabela de hotspots a um colega e confirme que ele chegaria às mesmas três prioridades lendo só o README.
