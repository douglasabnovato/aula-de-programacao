Relacional, Documento e o Meio-Termo

Aula 63 · Módulo 7: Avançado (Engenharia e Arquitetura Master) · ByteClass

A pergunta que decide

Não é "qual banco é melhor". É "como a aplicação lê este dado?" No relacional, modela-se pela estrutura do domínio. No documento, modela-se pela consulta.

O mesmo domínio, dois modelos

Relacional — normalizado

pedidos(id, cliente_id, total, criado_em)
itens_pedido(id, pedido_id, produto_id, qtd, preco)
produtos(id, nome, preco_atual)
clientes(id, nome, email)

-- Montar a tela do pedido:
SELECT p.*, c.nome, i.qtd, pr.nome
FROM pedidos p
JOIN clientes c   ON c.id = p.cliente_id
JOIN itens_pedido i ON i.pedido_id = p.id
JOIN produtos pr  ON pr.id = i.produto_id
WHERE p.id = 42;                              -- 3 JOINs

Documento — modelado pelo acesso

{
  "_id": 42,
  "criado_em": "2026-09-25T10:00:00Z",
  "total": 289.90,
  "cliente": { "id": 7, "nome": "Maria Souza", "email": "..." },
  "itens": [
    { "produto_id": 15, "nome": "Teclado", "qtd": 1, "preco": 189.90 },
    { "produto_id": 22, "nome": "Mouse",   "qtd": 2, "preco": 50.00 }
  ]
}

// Montar a tela do pedido: uma leitura, zero JOIN
db.pedidos.findOne({ _id: 42 })

O que cada modelo cobra

Relacional JOIN em toda leitura · dado sem duplicação · atualizar o nome do cliente é um UPDATE
Documento leitura direta · dado duplicado · atualizar o nome do cliente exige varrer os pedidos

Mas atenção: nem toda duplicação é erro

O preco dentro do item deve ser copiado, não referenciado. Ele é o preço daquela compra. Se apontasse para produtos.preco_atual, o pedido de janeiro mudaria de valor quando o produto subisse em março. Isso vale nos dois modelos — e é erro de modelagem, não de banco.

A consulta que o documento atende mal

-- Relacional: direto
SELECT pr.nome, SUM(i.qtd)
FROM itens_pedido i JOIN produtos pr ON pr.id = i.produto_id
GROUP BY pr.nome ORDER BY 2 DESC LIMIT 10;

-- Documento: precisa varrer todos os pedidos e desmontar os arrays

Consulta analítica que atravessa muitos documentos é onde o modelo embutido custa caro.

O meio-termo que quase ninguém considera

CREATE TABLE pedidos (
  id         serial PRIMARY KEY,
  cliente_id int NOT NULL REFERENCES clientes(id),
  total      numeric(10,2) NOT NULL,
  snapshot   jsonb NOT NULL,          -- o documento para a tela
  criado_em  timestamptz DEFAULT now()
);

CREATE INDEX idx_snapshot ON pedidos USING gin (snapshot);

-- Leitura direta da tela:
SELECT snapshot FROM pedidos WHERE id = 42;

-- E o relatório continua funcionando com SQL e transação.

PostgreSQL com jsonb entrega boa parte da flexibilidade de documento sem abrir mão de transação, JOIN e integridade referencial. Antes de trocar de banco, vale testar se o que você tem já resolve.
