Antes do índice

EXPLAIN ANALYZE
SELECT * FROM pedidos WHERE cliente_id = 4217;
Seq Scan on pedidos  (cost=0.00..2334.00 rows=19 width=45)
                     (actual time=0.412..18.903 rows=22 loops=1)
  Filter: (cliente_id = 4217)
  Rows Removed by Filter: 99978
Execution Time: 18.964 ms

Como ler isso

Seq Scanleu a tabela inteira, linha por linha
Rows Removed: 99978descartou 99.978 para devolver 22 — o desperdício
cost=a estimativa do planejador, antes de rodar
actual time=o que realmente aconteceu (só com ANALYZE)

Quando rows estimado e rows real divergem muito, as estatísticas estão velhas. Rode ANALYZE pedidos; antes de concluir qualquer coisa.

Depois do índice

CREATE INDEX idx_pedidos_cliente ON pedidos (cliente_id);

EXPLAIN ANALYZE
SELECT * FROM pedidos WHERE cliente_id = 4217;
Index Scan using idx_pedidos_cliente on pedidos
  (cost=0.29..8.51 rows=22 width=45)
  (actual time=0.031..0.048 rows=22 loops=1)
  Index Cond: (cliente_id = 4217)
Execution Time: 0.071 ms

De ~19 ms para ~0,07 ms. Duas ordens de grandeza, com uma linha.

Seq Scan nem sempre é problema

Se a consulta devolve 60% da tabela, ler tudo em sequência é mais rápido que pular de página em página pelo índice. O planejador sabe disso e escolhe certo. Seq Scan só é sintoma quando Rows Removed by Filter é muito maior que as linhas devolvidas.

O N+1, em código

// 101 idas ao banco
const pedidos = await db.query('SELECT * FROM pedidos LIMIT 100');
for (const p of pedidos) {
  p.cliente = await db.query('SELECT * FROM clientes WHERE id = $1', [p.cliente_id]);
}

// 1 ida ao banco
const pedidos = await db.query(`
  SELECT p.*, c.nome AS cliente_nome
  FROM pedidos p
  JOIN clientes c ON c.id = p.cliente_id
  LIMIT 100
`);

Cada ida ao banco custa a ida e a volta pela rede. Cem consultas de 1 ms com 2 ms de rede cada dão 300 ms; uma consulta de 5 ms dá 7 ms.
