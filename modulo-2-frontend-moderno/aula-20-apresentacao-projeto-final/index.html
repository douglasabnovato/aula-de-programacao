🗺️ 1. Escopo e Arquitetura do Projeto

🎯 Desafio

Você tem duas semanas para entregar o projeto final do módulo: uma aplicação React que junte rotas, formulário validado, consumo de API, estado global e deploy. Na turma anterior, os projetos que tentaram fazer tudo não terminaram nada. Como definir um escopo que caiba no prazo e uma arquitetura que você consiga explicar para a banca?

O projeto final começa pelo escopo: o problema, quem usa, como cada requisito do módulo aparece no sistema e o que fica de fora. A arquitetura é o mapa de rotas, a árvore de componentes e o lugar de cada estado, e o trabalho vira issues com critério de aceite num quadro.

  • 📄 Pensando em React — React O método de quebrar a interface em componentes e decidir onde cada estado vive.
  • 📄 Sobre issues — GitHub Docs Como issues registram tarefas, com listas de verificação e vínculos a pull requests.
  • 📄 Criar uma issue — GitHub Docs O passo a passo para abrir cada funcionalidade como uma issue.
  • 📄 Início rápido para Projects — GitHub Docs Como montar o quadro com colunas e datas para acompanhar o andamento.

  • ▶️ CURSO DE GESTÃO DE PROJETOS EP5: DEFINIR ESCOPO DE PROJETO Rogerio Lacerda · 12:14 — Mostra como definir e documentar o escopo de um projeto antes de começar a construir.

Siga os 10 passos abaixo para construir a prática aplicando os conceitos do bloco:

  1. Configuração do Ambiente: crie o repositório projeto-final-modulo-2 no GitHub e um quadro no GitHub Projects ligado a ele.
  2. Problema: escreva em três frases o problema de uma empresa fictícia, quem usa o sistema e o resultado esperado.
  3. Requisitos do Módulo: monte a tabela com os cinco requisitos (rotas com parâmetro, formulário validado, API com carregando e erro, Context e deploy) e onde cada um aparece.
  4. Fora do Escopo: liste pelo menos três funcionalidades que você não vai fazer e por quê.
  5. Mapa de Rotas: faça a tabela rota, página e dados, marcando quais rotas são protegidas.
  6. Árvore e Estados: desenhe a árvore de componentes e marque se cada estado vive na URL, num contexto ou no próprio componente.
  7. Erro Provocado: Issue Vaga: escreva a issue "Fazer o site", tente dizer quando ela termina e reescreva como "Formulário de reserva recusa horário ocupado".
  8. Backlog em Issues: abra uma issue por funcionalidade, cada uma com critério de aceite em lista de tarefas.
  9. Quadro e Datas: coloque as issues no quadro em A fazer, Fazendo e Feito e defina uma data-limite para cada semana.
  10. Validação e Testes: peça a um colega que confira se cada requisito tem ao menos uma issue; registre no README a seção Escopo gerada no canvas.
Concluiu todos os passos?

🔨 2. Construção, Qualidade e Entrega

🎯 Desafio

Faltando três dias para a apresentação, o projeto funciona no computador, mas o link publicado mostra uma tela branca, o README tem só o título que o Vite gerou e ninguém testou no celular. Como transformar código que funciona numa entrega que outra pessoa consegue abrir, entender e avaliar?

Entregar é ter o código versionado em pull requests, a aplicação publicada, um README que explica o que é, como rodar e quais decisões foram tomadas, e a qualidade verificada em tela pequena, no teclado e no contraste. Um checklist com evidência torna cada item conferível.

  • 📄 Sobre os READMEs — GitHub Docs Onde o README aparece e o que ele deve contar a quem chega ao repositório.
  • 📄 Sintaxe básica de escrita e formatação — GitHub Docs Títulos, tabelas, listas e blocos de código em Markdown para o README.
  • 📄 Sobre pull requests — GitHub Docs Como propor e revisar mudanças antes de irem para a branch principal.
  • 📄 WCAG 2.1 — Referência rápida — W3C Os critérios de acessibilidade usados no checklist, filtráveis por nível.

Siga os 10 passos abaixo para construir a prática aplicando os conceitos do bloco:

  1. Configuração do Ambiente: a partir de agora, crie uma branch por funcionalidade, como feature/formulario-reserva.
  2. Commits: faça commits pequenos, um assunto por commit, com mensagem no imperativo, como Adiciona checagem de conflito de horário.
  3. Pull Request: abra um pull request por branch descrevendo o que muda e como testar, mesmo trabalhando sozinho.
  4. Console Limpo: abra o projeto com o DevTools e corrija todos os erros e avisos do console, inclusive os de key.
  5. Erro Provocado: Tela Branca: abra o link publicado numa janela anônima, observe a tela branca quando a base não bate com o repositório e corrija.
  6. Três Larguras: confira o layout em 375px, 768px e 1280px e ajuste o que quebrar.
  7. Só Teclado: faça o fluxo principal usando só Tab, Enter e Espaço, conferindo o foco visível.
  8. Contraste: confira o contraste das cores principais contra o nível AA da WCAG e ajuste os tokens se preciso.
  9. README Completo: preencha as seções do modelo: descrição, link, funcionalidades, tecnologias, como rodar, decisões e próximos passos.
  10. Validação e Testes: complete o checklist de entrega com evidência em todos os itens; registre no README a seção Qualidade verificada.
Concluiu todos os passos?

🎤 3. Apresentação e Defesa Técnica

🎯 Desafio

Na apresentação, cada pessoa tem 7 minutos para mostrar o sistema e 3 minutos para perguntas. Na turma passada, metade gastou o tempo explicando a instalação do Vite, não mostrou o fluxo principal e travou quando a banca perguntou por que usou Context em vez de props. Como montar um roteiro que mostre valor em pouco tempo e preparar as respostas sobre decisões técnicas?

Uma apresentação técnica curta segue um roteiro: problema, demonstração do fluxo principal, uma decisão técnica com a alternativa descartada e o fechamento com limitações. A banca avalia por uma rubrica conhecida de antemão, e ensaiar com cronômetro e perguntas prováveis reduz o improviso.

  • 📄 Passando dados com contexto — React Inclui a seção sobre o que considerar antes de usar Context, base para defender essa escolha.
  • 📄 Escolhendo a estrutura do estado — React Princípios para justificar onde cada estado do projeto ficou.
  • 📄 Gerenciar o README do perfil — GitHub Docs Como apresentar o projeto no seu perfil depois da banca.
  • 📄 Fixar itens no perfil — GitHub Docs Como deixar o projeto final em destaque no portfólio.

Siga os 10 passos abaixo para construir a prática aplicando os conceitos do bloco:

  1. Configuração do Ambiente: tenha em mãos a rubrica da banca, o link publicado aberto e o roteiro em docs/roteiro-apresentacao.md.
  2. Abertura (1 min): escreva duas frases sobre o problema e para quem o sistema existe, sem falar de tecnologia.
  3. Demonstração (3 min): liste de três a quatro ações do fluxo principal feitas no link publicado, incluindo recarregar uma rota interna.
  4. Decisão Técnica (2 min): escolha uma decisão e escreva o que escolheu, o que descartou e o custo aceito.
  5. Fechamento (1 min): diga uma limitação atual e o próximo passo do projeto.
  6. Erro Provocado: Sem Cronômetro: ensaie sem marcar o tempo, depois ensaie com o cronômetro por blocos e compare a diferença.
  7. Perguntas Prováveis: prepare respostas curtas para cinco perguntas: Context, falha da API, rotas no deploy, acessibilidade e o que faria diferente.
  8. Plano B: grave um vídeo de dois minutos do fluxo principal e deixe prints no README para o caso de a internet falhar.
  9. Portfólio: fixe o repositório no seu perfil do GitHub e cite o projeto no README do perfil.
  10. Validação e Testes: faça um ensaio com um colega pontuando pela rubrica, ajuste até atingir sua nota-alvo dentro do tempo e registre no README o link dos slides ou do vídeo.
Concluiu todos os passos?
