🚀 1. Build de Produção, Variáveis de Ambiente e Deploy

🎯 Desafio

O site fictício do Cine Clube Paraibuna funciona no computador da desenvolvedora, mas ninguém mais consegue acessar. A URL da API está escrita direto no código com o endereço de testes, e na primeira publicação as rotas internas deram erro 404 ao recarregar. Como gerar a versão de produção, separar configurações por ambiente e publicar num serviço gratuito?

O npm run build gera em dist/ arquivos estáticos otimizados, prontos para qualquer hospedagem de arquivos. Variáveis com prefixo VITE_ entram no código no momento do build e são públicas. E uma SPA precisa que o servidor devolva o index.html para qualquer rota.

  • 📄 Building for Production — Vite O que o build faz, a opção base e como os arquivos finais são organizados.
  • 📄 Env Variables and Modes — Vite Arquivos .env por modo, o prefixo VITE_ e o aviso sobre não colocar segredos nelas.
  • 📄 Deploying a Static Site — Vite Guia oficial de publicação, incluindo o workflow pronto para o GitHub Pages.
  • 📄 Criar um site do GitHub Pages — GitHub Docs Como ativar o Pages no repositório, hospedagem gratuita para o portfólio.

Siga os 10 passos abaixo para construir a prática aplicando os conceitos do bloco:

  1. Configuração do Ambiente: no projeto React da aula, rode npm run build e abra a pasta dist para ver o que foi gerado.
  2. Pré-visualização: rode npm run preview e compare, no terminal, o tamanho dos arquivos com o que você escreveu.
  3. Arquivos por Modo: crie .env.development e .env.production, cada um com seu VITE_API_URL.
  4. Leitura Centralizada: crie src/config.js lendo import.meta.env uma vez e exportando um objeto config.
  5. Erro Provocado: Sem Prefixo: declare API_URL=... sem VITE_, mostre na tela e observe o undefined.
  6. Segredos Fora: acrescente *.local ao .gitignore e anote no código que nenhuma chave secreta pode ir para variáveis VITE_.
  7. Base do Repositório: no vite.config.js, defina base: '/cine-clube/' com o nome exato do repositório.
  8. Workflow de Deploy: crie .github/workflows/deploy.yml a partir do modelo do guia de deploy do Vite e escolha GitHub Actions como fonte em Settings → Pages.
  9. Rotas da SPA: recarregue uma rota interna publicada, veja o 404 e acrescente ao workflow o passo cp dist/index.html dist/404.html.
  10. Validação e Testes: abra o endereço publicado, navegue, recarregue uma rota interna e confira a API de produção na tela; registre no README o link público e os comandos de build.

⚡ 2. Renderizações, memo, useMemo e useCallback

🎯 Desafio

A página de programação do Cine Clube Paraibuna lista 2.000 sessões com filtro por texto. Trocar o tema trava a tela por um instante, e o React Developer Tools mostra que a lista inteira renderiza de novo mesmo sem nenhuma sessão ter mudado. Como descobrir o que está lento e evitar trabalho repetido sem espalhar otimização pelo código inteiro?

Otimização começa pela medição, com o Profiler do React Developer Tools. Depois, memo evita renderizar um componente cujas props não mudaram, useMemo guarda o resultado de um cálculo caro e useCallback mantém a mesma função entre renderizações para não anular o memo do filho.

  • 📄 memo — React Quando um componente memorizado pula a renderização e por que props novas a cada render anulam o ganho.
  • 📄 useCallback — React Como manter a mesma função entre renderizações e quando isso importa.
  • 📄 Profiler — React A medição de tempo de renderização, a mesma que a extensão mostra em gráfico.
  • 📄 React Developer Tools — React Instalação da extensão usada para inspecionar componentes e gravar o Profiler.

Siga os 10 passos abaixo para construir a prática aplicando os conceitos do bloco:

  1. Configuração do Ambiente: crie src/data/sessoes.js com gerarSessoes(2000) e um filtrarSessoes que espera 80 ms de propósito.
  2. Página Base: no App.jsx, crie os estados busca, claro e favoritos e mostre a lista filtrada.
  3. Medição Inicial: grave no Profiler uma digitação e um clique em Trocar tema e anote a duração de cada renderização.
  4. Erro Provocado: Trabalho Repetido: com um contador de execuções no filtro, clique em Trocar tema e observe o filtro rodar sem a busca ter mudado.
  5. Memorizando o Cálculo: envolva o filtro em useMemo(() => filtrarSessoes(SESSOES, busca), [busca]) e repita o clique.
  6. Memorizando a Lista: mova a lista para ListaSessoes.jsx, exporte com memo(ListaSessoes) e mostre um contador de renderizações nela.
  7. Erro Provocado: Função Nova: passe onFavoritar={(id) => ...} direto no JSX e observe a lista renderizar a cada troca de tema mesmo com memo.
  8. Callback Estável: use useCallback com atualização por função (setFavoritos((atuais) => ...)) e dependências vazias.
  9. Menos DOM: renderize só os 100 primeiros resultados com slice(0, 100) e mostre o total encontrado.
  10. Validação e Testes: grave o Profiler de novo com as mesmas ações e compare; registre no README a tabela antes e depois, em milissegundos.

📦 3. Code Splitting, Lazy Loading e Métricas

🎯 Desafio

O JavaScript do Cine Clube Paraibuna chegou a 900 KB porque a página de administração, com editor e gráficos, vai junto para todo visitante que só quer ver a programação. No celular com rede lenta, a primeira tela demora oito segundos. Como entregar primeiro só o necessário e carregar o resto quando for usado?

O lazy com import() dinâmico separa um componente num arquivo próprio, baixado só quando ele é renderizado, e o Suspense mostra um aviso enquanto isso. Imagens com loading lazy e dimensões reservadas completam o ajuste, e o Lighthouse mede o resultado.

  • 📄 lazy — React Como adiar o carregamento do código de um componente até a primeira renderização.
  • 📄 Suspense — React O componente que mostra um fallback enquanto o conteúdo carrega.
  • 📄 Lazy loading — MDN Divisão de código, imagens com loading lazy e outras formas de adiar recursos.
  • 📄 Optimize Largest Contentful Paint — web.dev A métrica da maior pintura de conteúdo e o que atrasa a primeira tela.

Siga os 10 passos abaixo para construir a prática aplicando os conceitos do bloco:

  1. Configuração do Ambiente: rode npm run build no projeto e anote o tamanho do arquivo JavaScript principal.
  2. Página Pesada: crie src/pages/Admin.jsx com o relatório de público e importe-a normalmente no App.jsx.
  3. Import Dinâmico: troque o import do topo por const Admin = lazy(() => import('./pages/Admin.jsx')).
  4. Erro Provocado: Sem Suspense: renderize <Admin /> sem nada em volta, abra a administração e leia o erro no console.
  5. Suspense: envolva com <Suspense fallback={<p>Carregando administração...</p>}>.
  6. Novo Build: rode npm run build e encontre em dist/assets o arquivo separado do Admin.
  7. Conferindo na Rede: com npm run preview e a aba Rede aberta, confirme que o arquivo do Admin só é baixado ao clicar em Administração.
  8. Imagens Adiadas: nos cartazes, use loading="lazy" com width e height definidos.
  9. Medição com Lighthouse: rode o Lighthouse no modo celular antes e depois da divisão e anote a nota de desempenho e o LCP.
  10. Validação e Testes: navegue entre as páginas com a rede em Slow 3G e confira o fallback; registre no README os tamanhos dos arquivos e as métricas antes e depois.
Concluiu todos os passos?
