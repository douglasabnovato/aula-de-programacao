🫱 1. Networking como Troca, Não como Pedido

🎯 Desafio

O aluno fictício Pedro Henrique foi ao encontro mensal de uma comunidade fictícia de desenvolvedores em Juiz de Fora, entregou seu currículo a seis pessoas e perguntou a cada uma 'tem vaga aí?'. Ninguém respondeu depois. A colega fictícia Tainá foi ao mesmo evento, fez perguntas sobre o trabalho de duas pessoas e, um mês depois, foi indicada para uma vaga. O que ela fez de diferente, e como repetir isso de propósito?

Rede profissional é feita de conversas em que as duas partes ganham algo: informação, ajuda, indicação ou simplesmente interesse genuíno. Perguntas abertas sobre o trabalho do outro geram conversa; pedidos diretos logo no início encerram. Manter contato depois do encontro, com algo útil, é o que transforma um nome em relação.

  • 📄 Comunidade — Stack Overflow Survey 2025 Como desenvolvedores participam de comunidades técnicas e o que buscam nelas.
  • 📄 Perguntas abertas — Nielsen Norman Group Como formular perguntas que fazem a outra pessoa contar, em vez de responder sim ou não.
  • 📄 O que é CNV — Center for Nonviolent Communication Observar, ouvir e pedir de forma clara: base para uma primeira conversa sem pressão.
  • 📄 Artigos do Center for Creative Leadership Material gratuito sobre relações profissionais, influência e desenvolvimento de carreira.

Siga os 10 passos abaixo para construir a prática aplicando os conceitos do bloco:

  1. Configuração do Ambiente: crie o arquivo rede.md com três seções: Comunidades, Conversas e Acompanhamento.
  2. Mapeando Comunidades: liste três comunidades, presenciais ou online, ligadas ao seu posicionamento, com frequência dos encontros.
  3. Escolhendo Uma: escolha a que você consegue frequentar por três meses seguidos e anote a data do próximo encontro.
  4. Apresentação Curta: adapte a versão de trinta segundos do seu posicionamento para uma apresentação de dez segundos.
  5. Perguntas Abertas: escreva cinco perguntas sobre o trabalho do outro, como que problema vocês estão resolvendo agora?
  6. Erro Provocado: simule com um colega uma abordagem que começa com 'tem vaga aí?' e depois outra que começa por uma pergunta aberta; compare quanto tempo cada conversa durou.
  7. Ajustando: defina que o pedido, se houver, só aparece depois que a outra pessoa falar do trabalho dela.
  8. Oferecendo Algo: liste três coisas que você pode oferecer mesmo sendo iniciante: ajuda na organização do evento, um resumo da palestra, um link útil.
  9. Acompanhamento: escreva a mensagem que você enviará em até dois dias depois do encontro, citando algo da conversa.
  10. Validação e Testes: vá a um encontro, registre as conversas e as mensagens enviadas e anote no README o que aconteceu um mês depois.
Concluiu todos os passos?

🌱 2. Contribuindo em Projetos da Comunidade

🎯 Desafio

A aluna fictícia Carla Brandão quer contribuir com um projeto de código aberto usado pela comunidade fictícia Dev Mantiqueira, mas abriu o repositório, viu centenas de arquivos e fechou. Um colega abriu um Pull Request enorme mudando a formatação de tudo e teve a contribuição recusada. Qual é o tamanho certo da primeira contribuição e como ela chega a ser aceita?

Contribuir com projetos da comunidade é uma das formas mais concretas de ser visto trabalhando: o histórico fica público, e mantenedores passam a reconhecer seu nome. A primeira contribuição costuma ser pequena, como corrigir documentação ou um erro descrito numa issue. Os guias de revisão do Google explicam por que mudanças pequenas e bem descritas são aceitas mais rápido.

  • 📄 Guia do autor de mudanças — Google Engineering Practices Como escrever uma mudança pequena, com descrição clara, que alguém consiga revisar.
  • 📄 Como escrever comentários de revisão — Google Como os revisores comentam e como responder a eles de forma produtiva.
  • 📄 Guia de Code Review — thoughtbot Regras práticas de tom para quem envia e para quem revisa.
  • 📄 Entendendo o GitHub Actions — GitHub Docs Por que a sua contribuição roda testes automáticos antes de alguém olhar.

  • ▶️ Como contribuir com projetos open-source Mateus Guimarães - PT · 23:34 — Explica como encontrar projetos open source e começar a contribuir.

Siga os 10 passos abaixo para construir a prática aplicando os conceitos do bloco:

  1. Configuração do Ambiente: escolha um projeto aberto que você já usou, ou um repositório da própria turma, e leia o README e o arquivo de contribuição, se existir.
  2. Rodando Localmente: faça um fork, clone e siga as instruções até o projeto rodar na sua máquina.
  3. Encontrando a Tarefa: procure uma issue marcada para iniciantes ou uma correção de documentação que você mesmo encontrou ao rodar.
  4. Avisando: comente na issue que você vai trabalhar nela, antes de começar.
  5. Branch Própria: crie uma branch com nome descritivo, como docs/corrige-comando-instalacao.
  6. Erro Provocado: junte na mesma branch a correção e uma reformatação de vários arquivos, veja o tamanho do diff e imagine-se revisando aquilo.
  7. Ajustando: desfaça a reformatação e deixe só a mudança da issue, com commits pequenos.
  8. Descrição do Pull Request: escreva o que mudou, por que e como testar, com o número da issue.
  9. Respondendo a Revisão: responda cada comentário do revisor: aceite, pergunte ou explique o motivo técnico.
  10. Validação e Testes: confirme que as verificações automáticas passaram, registre o link do Pull Request no README e o que aprendeu com a revisão.
Concluiu todos os passos?

✍️ 3. Marca Pessoal por Meio de Escrita Técnica

🎯 Desafio

O desenvolvedor fictício Mateus Rangel aprendeu a resolver um problema de CORS que tomou dois dias da turma, mas a solução ficou só na cabeça dele. Seis meses depois, numa entrevista, perguntaram 'como você aprende e compartilha?', e ele não tinha nada para mostrar. Como transformar o que se aprende em material público que prova competência sem expor dados de ninguém?

Marca pessoal, para quem é técnico, é o que as pessoas encontram quando procuram seu nome: projetos, textos e contribuições. Escrever sobre um problema real que você resolveu é a forma mais direta de mostrar raciocínio. Publicar num site próprio com GitHub Pages mantém o conteúdo sob seu controle, e o cuidado com acessibilidade e com dados de terceiros faz parte da qualidade do texto.

  • 📄 Criando um site com GitHub Pages — GitHub Docs Publicar um blog ou portfólio gratuito a partir de um repositório.
  • 📄 Fonte de publicação do GitHub Pages — GitHub Docs Escolher a branch e a pasta de onde o site é publicado.
  • 📄 Referência rápida da WCAG 2.1 — W3C Critérios de acessibilidade que valem também para textos: títulos, contraste e texto alternativo.
  • 📄 LGPD compilada — Planalto Por que prints de sistema com dados de clientes ou colegas não entram em publicação.

Siga os 10 passos abaixo para construir a prática aplicando os conceitos do bloco:

  1. Configuração do Ambiente: crie um repositório para o seu site e ative o GitHub Pages seguindo a documentação oficial.
  2. Escolhendo o Assunto: escolha um problema real que você resolveu na trilha e que levou mais de uma hora.
  3. Estrutura: organize o texto em: o problema, o que tentei, o que funcionou, por que funcionou e referências.
  4. Código Mínimo: inclua apenas o trecho de código necessário, com a versão das ferramentas usadas.
  5. Imagens: se usar captura de tela, escreva texto alternativo que descreva o que a imagem mostra.
  6. Erro Provocado: insira uma captura de tela do projeto de um colega ou de um sistema de trabalho sem editar e confira, pela LGPD, que tipo de dado ficou exposto.
  7. Ajustando: troque por um exemplo com dados fictícios ou recorte a imagem até não sobrar dado pessoal.
  8. Revisão Técnica: peça a um colega que siga o artigo do zero e aponte o primeiro passo que não funcionou.
  9. Publicação: publique o artigo e compartilhe o link no LinkedIn com duas frases sobre o problema, sem exagero.
  10. Validação e Testes: confira o site num celular, verifique títulos e texto alternativo com a referência da WCAG e registre o link no README do perfil.
Concluiu todos os passos?
