Volumes e Variáveis em Execução

Aula 32 · Módulo 4: Fullstack, DevOps e Projeto Final · ByteClass

A perda que todo mundo sofre uma vez

docker run -d -p 3000:3000 --name api minha-api
# criar tarefas pela API...
docker stop api && docker rm api
docker run -d -p 3000:3000 --name api minha-api
# as tarefas sumiram

O sistema de arquivos do contêiner morre com ele. Isso é projeto, não defeito.

Com volume nomeado

docker volume create dados-api

docker run -d \
  --name api \
  -p 3000:3000 \
  -v dados-api:/app/dados \
  --env-file .env \
  minha-api

Agora o ciclo parar / remover / subir preserva o que estiver em /app/dados.

Bind mount, para desenvolver

docker run -it --rm \
  -p 3000:3000 \
  -v "$(pwd)":/app \
  -v /app/node_modules \
  minha-api npm run dev

O segundo -v protege o node_modules da imagem de ser encoberto pelo da sua máquina — que pode ter sido instalado em outro sistema operacional.

Diagnóstico

docker logs -f api           # acompanhar a saída
docker exec -it api sh       # entrar no contêiner em execução
docker inspect api           # configuração completa em JSON
docker volume inspect dados-api

A pegadinha do localhost

Dentro do contêiner, localhost é o próprio contêiner — não a sua máquina nem outro contêiner. Um serviço falar com o outro por localhost é o erro número um de quem está começando. A solução vem na aula 34, com Docker Compose e rede nomeada.
