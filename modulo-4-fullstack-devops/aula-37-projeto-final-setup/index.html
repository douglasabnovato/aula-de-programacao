🎯 1. Escopo, Problema e MVP

🎯 Desafio

O salão fictício Studio Lírio anota os horários num caderno e perde cerca de oito clientes por semana por remarcação esquecida. Você tem quatro aulas para entregar um sistema fullstack no ar, e a lista de desejos da dona já tem 25 itens, de agenda a programa de fidelidade. O que entra na primeira versão para que ela resolva o problema de verdade e caiba no prazo?

Projeto final não é a soma de tudo que se aprendeu, é um problema resolvido de ponta a ponta. O escopo define o problema, quem sofre com ele, a menor versão que já entrega valor e, com a mesma clareza, o que fica de fora.

  • 📄 The Scrum Guide — scrumguides.org Backlog do produto, incremento e Definição de Pronto: os artefatos que organizam o que entra em cada entrega.
  • 📄 Princípios do Manifesto Ágil — agilemanifesto.org Software funcionando como medida de progresso e simplicidade como a arte de maximizar o trabalho não feito.
  • 📄 Yagni — Martin Fowler Por que não construir agora a funcionalidade que talvez seja útil depois.
  • 📄 Guia Kanban — kanbanguides.org Como visualizar o fluxo de trabalho e limitar o que está em andamento ao mesmo tempo.
🎥 Vídeos de apoio
  • ▶️ O QUE É MVP (PRODUTO MÍNIMO VIÁVEL)? EXEMPLOS PRÁTICOS Gabriel Valle · 5:48 — Explica o que é MVP com exemplos práticos de como reduzir a primeira versão ao essencial.
  • ▶️ Como Fazer um Escopo de Projeto: Um Guia para Iniciantes Cafe Com Inovação · 14:30 — Mostra como definir o escopo de um projeto: problema, entregas e limites.

Siga os 10 passos abaixo para construir a prática aplicando os conceitos do bloco:

  1. Configuração do Ambiente: crie o repositório do projeto final no GitHub com um docs/ESCOPO.md vazio e um quadro em GitHub Projects com as colunas A fazer, Fazendo e Feito.
  2. O Problema em uma Frase: escreva quem sofre, com o quê e quanto isso custa hoje, sem citar tecnologia.
  3. Pessoas Usuárias: descreva no máximo dois perfis que usam o sistema e o que cada um precisa conseguir fazer.
  4. Lista Completa: liste todas as funcionalidades que vierem à cabeça, sem filtrar.
  5. Corte do MVP: marque só o que é indispensável para resolver o problema da primeira frase: o alvo é de 3 a 5 histórias.
  6. Erro Provocado: estime em horas cada história marcada, some e compare com as horas das aulas 38 e 39: se passou, o corte ainda não aconteceu.
  7. Fora do Escopo: crie a seção Fora do Escopo com o que foi cortado e o motivo de cada corte.
  8. Critérios de Aceite: escreva para cada história de 2 a 4 critérios verificáveis no formato Dado, Quando, Então.
  9. Backlog no Quadro: transforme cada história em uma issue com os critérios no corpo e coloque todas em A fazer.
  10. Validação e Testes: apresente o escopo a um colega em dois minutos, peça que ele diga de volta qual problema o sistema resolve e registre no README a frase final do problema.
Concluiu todos os passos?

🏛️ 2. Arquitetura, Contrato e Decisões Registradas

🎯 Desafio

Com o escopo do Studio Lírio fechado, a dupla de frontend começou a tela de agenda esperando o campo 'data' e a dupla de backend entregou 'inicio' e 'fim' em outro formato. Duas tardes de trabalho foram refeitas, e ninguém lembra por que o banco escolhido foi PostgreSQL. Como fixar as decisões de arquitetura e o contrato antes de escrever a primeira rota?

Arquitetura é o conjunto de decisões difíceis de mudar depois. Um desenho simples das partes, o contrato da API escrito antes do código e um registro curto de cada decisão evitam retrabalho e respondem ao 'por quê' meses depois.

  • 📄 Software Architecture Guide — Martin Fowler O que é arquitetura, por que ela importa e onde estão as decisões que custam caro mudar.
  • 📄 Architectural Decision Records — adr.github.io O formato de registro de decisão, com modelos prontos e exemplos.
  • 📄 OpenAPI Specification — swagger.io O formato padrão para descrever rotas, corpos e respostas de uma API.
  • 📄 Presentation Domain Data Layering — Martin Fowler A divisão em apresentação, domínio e dados que organiza tanto o frontend quanto a API.
🎥 Vídeos de apoio
  • ▶️ Documentando decisões técnicas com ADRs (Architecture Decision Record) Matheus Castiglioni · 15:43 — Mostra como documentar decisões técnicas com ADRs e por que registrá-las.
  • ▶️ O que são ADRs (Architecture Decision Records)? André Secco · 16:16 — Explica o que são Architecture Decision Records e como estruturar um.

Siga os 10 passos abaixo para construir a prática aplicando os conceitos do bloco:

  1. Configuração do Ambiente: crie docs/ARQUITETURA.md, docs/openapi.yaml e a pasta docs/adr/ no repositório do projeto.
  2. Desenho das Partes: desenhe as caixas do sistema: navegador, frontend estático, API, banco e o sentido de cada seta.
  3. Hospedagem de Cada Parte: anote ao lado de cada caixa onde ela vai rodar, escolhendo opções gratuitas: Vercel, Netlify ou GitHub Pages para o front; Render free para a API; Neon ou Supabase free para o banco.
  4. Modelo de Dados: liste as tabelas com colunas, tipos e as ligações entre elas, partindo das histórias do escopo.
  5. Contrato Primeiro: descreva no openapi.yaml cada rota do MVP com método, caminho, corpo de entrada e resposta de sucesso.
  6. Formato de Erro: defina um único esquema de erro e use-o em todas as respostas 4xx e 5xx do contrato.
  7. Erro Provocado: peça a um colega que escreva o JSON que a tela de listagem espera sem olhar o contrato e compare campo a campo.
  8. Primeiro ADR: escreva docs/adr/0001-banco-postgresql.md com contexto, decisão e consequências.
  9. Segundo ADR: escreva docs/adr/0002-autenticacao-jwt.md registrando também a alternativa descartada.
  10. Validação e Testes: cole o openapi.yaml no Swagger Editor, corrija até não haver erro de validação e registre no README o link para a pasta docs/.
Concluiu todos os passos?

🧰 3. Setup do Repositório e Esteira Desde o Primeiro Dia

🎯 Desafio

No projeto do Studio Lírio, cada integrante criou a própria estrutura de pastas e a primeira integração entre as partes aconteceu na véspera da entrega. Metade dos commits foi direto na main e o projeto só rodava na máquina de quem escreveu. Como deixar o repositório pronto para o time trabalhar em paralelo desde o primeiro dia?

Setup é o investimento que paga todas as aulas seguintes: estrutura de pastas combinada, ambiente que sobe com um comando, esteira que verifica cada push e regras que protegem o ramo principal.

  • 📄 Twelve-Factor — Base de Código Uma base de código rastreada no controle de versão e muitos deploys a partir dela.
  • 📄 Twelve-Factor — Dependências Declarar e isolar dependências para que o projeto rode igual em qualquer máquina.
  • 📄 Docker Compose — Docker Docs A página de entrada do Compose, para o ambiente local subir inteiro com um comando.
  • 📄 GitHub Actions — Início Rápido O workflow mínimo, ponto de partida da esteira do projeto final.

Siga os 10 passos abaixo para construir a prática aplicando os conceitos do bloco:

  1. Configuração do Ambiente: clone o repositório do projeto final e crie as pastas api/, web/ e docs/ na raiz.
  2. Esqueleto da API: dentro de api/, inicie o projeto Node com Express e uma rota GET /saude respondendo 200.
  3. Esqueleto do Frontend: dentro de web/, crie o projeto React com Vite e uma tela que chama /saude e mostra o resultado.
  4. Configuração de Exemplo: crie .env.example em cada parte com todas as variáveis e valores fictícios, e coloque .env no .gitignore.
  5. Ambiente Local: escreva o compose.yaml com db, api e healthcheck, como na aula 34.
  6. Esteira Mínima: crie .github/workflows/ci.yml que instala e roda o lint das duas partes a cada push e pull request.
  7. Proteção do Ramo: ative a regra que exige pull request e esteira verde para mesclar na main.
  8. Erro Provocado: tente um git push direto na main e leia a recusa do GitHub.
  9. README Inicial: escreva no README como clonar, configurar o .env e subir o projeto em três comandos.
  10. Validação e Testes: peça a um colega que clone o repositório numa máquina limpa seguindo só o README e registre no próprio README quanto tempo ele levou até ver a tela chamando /saude.
Concluiu todos os passos?
