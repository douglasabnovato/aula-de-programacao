# Arquitetura — Agenda Lírio

## Partes
Navegador → Frontend React (estático) → API Node/Express → PostgreSQL

## Onde cada parte roda (hospedagem gratuita)
| Parte     | Local de desenvolvimento | Produção                          |
|-----------|--------------------------|-----------------------------------|
| Frontend  | Vite em localhost:5173   | Vercel (ou Netlify / GitHub Pages)|
| API       | Compose, porta 3000      | Render — plano free               |
| Banco     | Compose, postgres:16     | Neon ou Supabase — plano free     |

## Modelo de dados
- profissionais (id, nome, ativo)
- usuarios (id, email, senha_hash, papel)
- agendamentos (id, profissional_id → profissionais.id, cliente_nome, inicio, fim, status)

## Limites conhecidos do plano gratuito
- A API no Render free hiberna sem tráfego; a primeira requisição depois disso demora.
- O banco gratuito tem limite de armazenamento; o volume do projeto cabe com folga.

docs/openapi.yaml (trecho)

# Início: openapi.yaml — contrato das rotas de agendamento da Agenda Lírio
openapi: 3.0.3
info:
  title: Agenda Lírio API
  version: 0.1.0
paths:
  /agendamentos:
    get:
      summary: Lista os agendamentos de um dia
      parameters:
        - name: data
          in: query
          required: true
          schema: { type: string, format: date }
      responses:
        "200":
          description: Agendamentos do dia
          content:
            application/json:
              schema:
                type: array
                items: { $ref: "#/components/schemas/Agendamento" }
    post:
      summary: Cria um agendamento sem conflito de horário
      requestBody:
        required: true
        content:
          application/json:
            schema: { $ref: "#/components/schemas/NovoAgendamento" }
      responses:
        "201":
          description: Criado
          content:
            application/json:
              schema: { $ref: "#/components/schemas/Agendamento" }
        "409":
          description: Horário indisponível
          content:
            application/json:
              schema: { $ref: "#/components/schemas/Erro" }
components:
  schemas:
    NovoAgendamento:
      type: object
      required: [profissionalId, clienteNome, inicio, fim]
      properties:
        profissionalId: { type: integer }
        clienteNome: { type: string }
        inicio: { type: string, format: date-time }
        fim: { type: string, format: date-time }
    Agendamento:
      allOf:
        - $ref: "#/components/schemas/NovoAgendamento"
        - type: object
          properties:
            id: { type: integer }
            status: { type: string, enum: [marcado, cancelado] }
    Erro:
      type: object
      required: [erro]
      properties:
        erro: { type: string }
# Fim de openapi.yaml

# 0001 — Usar PostgreSQL como banco de dados

## Status
Aceito

## Contexto
Agendamentos não podem se sobrepor para o mesmo profissional. A regra precisa
ser garantida mesmo com duas recepcionistas salvando ao mesmo tempo.
O time já usou PostgreSQL no Módulo 3, e há planos gratuitos no Neon e no Supabase.

## Decisão
Usar PostgreSQL, com restrição no banco para impedir sobreposição de horário.

## Alternativas descartadas
- MongoDB: garantir a regra de não sobreposição ficaria no código da API, sujeito a corrida entre requisições.

## Consequências
- A regra de conflito fica protegida no banco, não só na API.
- Migrações de esquema passam a ser necessárias a cada mudança de tabela.
<!-- Fim de ADR 0001 -->

O que observar

  • O contrato devolve 409 para conflito: o frontend sabe exatamente que mensagem mostrar.
  • A tabela de hospedagem registra o limite do plano gratuito antes de ele virar surpresa na apresentação.
  • O ADR registra a alternativa descartada — é a primeira pergunta que uma banca faz.
