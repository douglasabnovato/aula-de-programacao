📘 1. README, Portfólio e a Prova Pública do Projeto

🎯 Desafio

Uma recrutadora fictícia da empresa Horizonte Sistemas abre o repositório da Agenda Lírio entre outros 40 candidatos e dá a cada um cerca de dois minutos. O README atual começa com 'npm install' e não diz que problema o projeto resolve nem onde ver funcionando. O que precisa estar no topo do repositório para esses dois minutos contarem a seu favor?

O README é a primeira apresentação do projeto e continua trabalhando depois da formatura. Ele precisa responder, nesta ordem, o que é, para quem, onde ver funcionando, como foi construído e como rodar, com as decisões técnicas a um clique.

  • 📄 Hierarquia Visual — Nielsen Norman Group Como organizar conteúdo para que quem escaneia encontre o essencial primeiro.
  • 📄 Architectural Decision Records — adr.github.io O formato dos registros de decisão que o README aponta como prova de raciocínio técnico.
  • 📄 OpenAPI Specification — swagger.io O contrato da API publicado junto do projeto, legível por pessoas e ferramentas.
  • 📄 Learn Accessibility — web.dev O curso de referência para revisar a acessibilidade da aplicação antes de expô-la publicamente.

  • ▶️ Como fazer um README para portfolio no Github DevSuperior · 14:37 — Mostra como montar um README de projeto voltado para portfólio no GitHub.

Siga os 10 passos abaixo para construir a prática aplicando os conceitos do bloco:

  1. Configuração do Ambiente: abra o README atual do projeto final e a aplicação publicada lado a lado.
  2. Primeira Linha: escreva o nome do projeto e uma frase com o problema resolvido e para quem, sem citar tecnologia.
  3. Prova Visual: grave um GIF curto do fluxo principal e coloque logo abaixo da primeira linha, com texto alternativo.
  4. Links que Importam: acrescente os links da aplicação publicada, do contrato OpenAPI e da pasta de ADRs.
  5. Tecnologias com Motivo: liste a stack em uma tabela com uma coluna dizendo por que cada escolha foi feita.
  6. Erro Provocado: peça a um colega que leia o README por 60 segundos e diga o que o projeto faz; se ele citar só a tecnologia, o topo ainda não funciona.
  7. Como Rodar: reduza a instalação local a no máximo cinco comandos, testados numa máquina limpa.
  8. Limites e Próximos Passos: escreva o que ficou fora do escopo e o que a próxima versão traria.
  9. Repositório Organizado: preencha a descrição e os tópicos do repositório no GitHub e fixe o projeto no seu perfil.
  10. Validação e Testes: abra o repositório numa aba anônima pelo celular, confira que imagens e links funcionam e registre no próprio README a data da versão apresentada.
Concluiu todos os passos?

🎤 2. Pitch e Demonstração ao Vivo

🎯 Desafio

Cada equipe terá sete minutos diante da banca e da turma, com a dona do Studio Lírio convidada na plateia. No ensaio, uma equipe gastou cinco minutos explicando a estrutura de pastas e a demonstração travou no login porque a API do plano gratuito estava hibernando. Como contar a história do projeto em sete minutos e garantir que a demonstração funcione na hora?

Pitch é uma história com começo, meio e fim: o problema de alguém, a solução funcionando e o que foi aprendido. A demonstração ao vivo é a prova, e por isso precisa de roteiro, dados de exemplo preparados e um plano para quando algo falhar.

  • 📄 Definição de Experiência do Usuário — Nielsen Norman Group Por que começar pelo que muda para quem usa, e não pelo que foi programado.
  • 📄 Leis de UX — lawsofux.com Princípios de percepção que valem para os slides: menos elementos, uma ideia por tela.
  • 📄 Contraste Mínimo — W3C WCAG 2.1 O critério de contraste que garante slides e tela legíveis no projetor da sala.
  • 📄 10 Heurísticas de Usabilidade — Nielsen Norman Group A revisão rápida da interface antes de mostrá-la para quem nunca a viu.
🎥 Vídeos de apoio
  • ▶️ Pitch Projeto Aplicado - Arquitetura de Software e Soluções - XPE Daniel Wisky · 9:47 — Exemplo de pitch de um projeto aplicado de arquitetura de software apresentado em poucos minutos.
  • ▶️ Como Fazer um Pitch de Excelência | Na Prática e Exame Na Prática · 3:31 — Apresenta um roteiro curto para montar um pitch objetivo com começo, meio e fim.

Siga os 10 passos abaixo para construir a prática aplicando os conceitos do bloco:

  1. Configuração do Ambiente: abra o modelo de roteiro da atividade 2 e defina quem da equipe fala em cada bloco.
  2. Abertura com o Problema: escreva os primeiros 60 segundos contando a situação do cliente com o número do escopo, sem nenhuma tela de código.
  3. Roteiro da Demonstração: liste os cliques exatos do fluxo principal, do login ao resultado, com os dados de exemplo que serão usados.
  4. Dados Preparados: crie no banco de produção os registros fictícios que a demonstração precisa, com nomes que façam sentido para o salão.
  5. Uma Decisão Técnica: escolha um único ADR para contar em 60 segundos: o problema, a escolha e o que ela custou.
  6. Slides Mínimos: monte no máximo cinco slides, uma ideia por slide, e confira o contraste do texto com o fundo.
  7. Erro Provocado: ensaie a demonstração com a API recém-hibernada e cronometre quanto tempo a tela fica carregando.
  8. Plano B: acorde a API cinco minutos antes, deixe o vídeo do fluxo pronto numa aba e combine a frase de transição se algo falhar.
  9. Ensaio Cronometrado: apresente para outra equipe com cronômetro visível e anote onde passou do tempo.
  10. Validação e Testes: faça o ensaio final dentro de sete minutos, colete duas sugestões da equipe ouvinte e registre no README o link dos slides e do vídeo.
Concluiu todos os passos?

🎓 3. Defesa Técnica, Feedback e Próximos Passos

🎯 Desafio

Depois do pitch, a banca pergunta à equipe da Agenda Lírio por que o token dura oito horas, o que acontece se duas recepcionistas marcarem o mesmo horário e o que fariam diferente. Um integrante responde que 'foi o jeito que deu', e outro fica em silêncio porque não escreveu aquela parte. Como se preparar para defender cada decisão, receber a crítica e sair da formatura com um plano para os próximos meses?

Defender um projeto é mostrar que as escolhas foram feitas com consciência, inclusive as que ficaram abaixo do ideal. A banca avalia raciocínio, não perfeição, e o feedback recebido vira o primeiro item do plano de estudo depois do curso.

  • 📄 Como Escrever Comentários de Revisão — Google O tom de uma crítica técnica útil, que também ensina a recebê-la.
  • 📄 Intenção e Impacto no Feedback — Center for Creative Leadership O método para dar e receber feedback focado em situação, comportamento e impacto.
  • 📄 Technical Debt Quadrant — Martin Fowler Como falar da dívida técnica assumida de propósito, com prudência, na defesa.
  • 📄 Stack Overflow Developer Survey O retrato anual das tecnologias e práticas de mercado, útil para escolher o próximo estudo.

Siga os 10 passos abaixo para construir a prática aplicando os conceitos do bloco:

  1. Configuração do Ambiente: abra a rubrica de avaliação da atividade 3 e leia cada critério em voz alta com a equipe.
  2. Mapa de Autoria: liste quem escreveu cada parte do sistema e garanta que todos consigam explicar as partes centrais, não só as próprias.
  3. Perguntas Prováveis: escreva dez perguntas que a banca pode fazer, uma para cada ADR e uma para cada regra de negócio crítica.
  4. Respostas em Três Frases: responda cada pergunta com a decisão, o motivo e o custo aceito.
  5. Dívida Assumida: liste três limitações conhecidas do projeto e o que seria feito com mais tempo.
  6. Erro Provocado: faça uma banca simulada em que outra equipe pergunta sobre a parte que você não escreveu e note onde a resposta travou.
  7. Recebendo a Crítica: durante a banca real, anote cada crítica sem rebater na hora e agradeça ao final.
  8. Autoavaliação: preencha a rubrica sobre o próprio projeto e compare com a nota e os comentários da banca.
  9. Plano de 90 Dias: escolha uma evolução do projeto e um tema de estudo a partir das críticas, com metas mensais verificáveis.
  10. Validação e Testes: publique no README a seção Próximos Passos com o plano de 90 dias e registre a data da formatura como marco da versão 1.0 do projeto.
Concluiu todos os passos?
