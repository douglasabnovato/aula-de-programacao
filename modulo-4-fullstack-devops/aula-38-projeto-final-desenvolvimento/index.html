🗄️ 1. Modelo de Dados e Rotas do Núcleo

🎯 Desafio

Na Agenda Lírio, a primeira versão da rota de criar agendamento aceitou dois horários sobrepostos para a mesma profissional, e a busca da agenda do dia levou quatro segundos com mil registros de teste. O contrato está pronto desde a aula passada. Como construir as rotas do núcleo para que respeitem o contrato, protejam a regra de negócio e continuem rápidas com dado de verdade?

O núcleo do projeto são as poucas rotas que resolvem o problema do escopo. Elas nascem do contrato, gravam num esquema versionado por migrações, validam a entrada e deixam o banco garantir o que não pode dar errado.

  • 📄 Índices — documentação do PostgreSQL Quando um índice acelera a consulta e qual o custo dele na escrita.
  • 📄 Injection Prevention — OWASP Por que consulta parametrizada é a defesa principal contra injeção de SQL.
  • 📄 Tratamento de Erros no Express O middleware de erro único que transforma falhas do banco em respostas do contrato.
  • 📄 Códigos de Status HTTP — MDN Qual status devolver em cada situação prevista no contrato: 201, 400, 404 e 409.
🎥 Vídeos de apoio
  • ▶️ Aulão de Migrations no Sequelize LuizTools · 39:52 — Explica migrations para versionar o esquema do banco, com exemplos no Sequelize.
  • ▶️ Vincular Node.js com Express ao PostgreSQL via Prisma - tutorial completo - Aula 03 Dev. Odair Michael · 56:37 — Conecta uma API Express ao PostgreSQL via Prisma, do modelo de dados às rotas.

Siga os 10 passos abaixo para construir a prática aplicando os conceitos do bloco:

  1. Configuração do Ambiente: suba o projeto com docker compose up, abra o docs/openapi.yaml ao lado e crie a pasta api/migracoes/.
  2. Primeira Migração: escreva 001_criar_tabelas.sql com as tabelas do ARQUITETURA.md, chaves estrangeiras e NOT NULL onde o dado é obrigatório.
  3. Aplicando a Migração: crie o script npm run migrar que executa os arquivos da pasta em ordem e registre quais já rodaram numa tabela de controle.
  4. Camadas: organize cada recurso em rota, controlador e repositório, como no Módulo 3.
  5. Rota de Listagem: implemente o GET do núcleo exatamente com os campos e o formato do contrato.
  6. Rota de Criação: implemente o POST validando a entrada e devolvendo 400 com o esquema de erro do contrato.
  7. Erro Provocado: crie dois registros que violam a regra de negócio principal ao mesmo tempo e confirme que a validação só no código deixou passar.
  8. Regra no Banco: acrescente uma migração 002 com a restrição no banco e traduza a violação para 409 no middleware de erro.
  9. Índice da Consulta Principal: insira mil registros de teste, rode EXPLAIN ANALYZE na listagem, crie o índice na coluna filtrada e compare o tempo.
  10. Validação e Testes: percorra cada rota do contrato com o Thunder Client ou Insomnia, confira status e formato, mova a issue para Feito e registre no README o tempo da consulta antes e depois do índice.
Concluiu todos os passos?

🔐 2. Autenticação e Integração com o Frontend

🎯 Desafio

A recepção do Studio Lírio vai usar a Agenda Lírio num computador compartilhado, e qualquer pessoa que descobrir o endereço da API consegue hoje cancelar agendamentos. Ao mesmo tempo, a tela de agenda ainda mostra dados fixos no código. Como proteger as rotas e ligar o frontend à API real sem deixar a sessão exposta?

Autenticação responde quem é a pessoa; autorização responde o que ela pode fazer. Com senha guardada como hash, token assinado com prazo e tratamento do 401 no frontend, o fluxo completo fica protegido de ponta a ponta.

  • 📄 Authentication Cheat Sheet — OWASP Mensagens de erro de login, limite de tentativas e o que não fazer ao autenticar.
  • 📄 Password Storage Cheat Sheet — OWASP Por que a senha vira hash lento com sal e nunca é guardada nem registrada em texto.
  • 📄 Introdução ao JWT — jwt.io As três partes do token, o que a assinatura garante e o que ela não esconde.
  • 📄 CORS — MDN Por que o navegador bloqueia a chamada entre origens e como a API libera só o frontend certo.

  • ▶️ Autenticação Segura com JWT no Node.js e React (Access Token + Expiration) Hashtag Dev · 36:30 — Implementa autenticação com JWT entre uma API Node.js e um frontend React, com expiração do token.
  • ▶️ Estratégias de autenticação entre front-end e back-end com JWT (cookies storage) Rocketseat · 6:18 — Compara estratégias de guardar o JWT no front-end, como cookies e storage.

Siga os 10 passos abaixo para construir a prática aplicando os conceitos do bloco:

  1. Configuração do Ambiente: na API, rode npm install bcrypt jsonwebtoken cors e acrescente JWT_SECRET ao .env.example com valor fictício.
  2. Cadastro Inicial: crie um script de semente que cadastra uma usuária de teste com bcrypt.hash e custo 10.
  3. Rota de Login: crie POST /auth/login que compara a senha com bcrypt.compare e devolve um token com expiresIn: '8h'.
  4. Mensagem Única: responda 401 com a mesma mensagem para e-mail inexistente e senha errada.
  5. Middleware de Autenticação: leia o cabeçalho Authorization: Bearer, valide com jwt.verify e guarde o usuário em req.usuario.
  6. Protegendo as Rotas: aplique o middleware às rotas de escrita e deixe pública só a consulta de horários livres.
  7. Erro Provocado: no frontend, chame a API sem configurar CORS e leia o bloqueio no console do navegador.
  8. Origem Liberada: configure cors({ origin: process.env.ORIGEM_FRONT }) e confirme que a chamada passa só dessa origem.
  9. Frontend Ligado: troque os dados fixos pela camada src/api/cliente.js da aula 31, enviando o token e tratando carregando, erro e vazio.
  10. Validação e Testes: percorra o roteiro de testes da atividade 2, incluindo token expirado e token alterado, e registre no README como o frontend reage a cada 401.
Concluiu todos os passos?

🧪 3. Testes, Pull Requests e Revisão em Dupla

🎯 Desafio

Na véspera da entrega, a correção de um bug no cadastro da Agenda Lírio quebrou a remarcação e ninguém percebeu até a apresentação de ensaio. Os pull requests do time têm título 'ajustes' e são aprovados em trinta segundos. Como fazer a esteira e a revisão entre colegas pegarem o problema antes de ele chegar na main?

Teste automatizado prova que o critério de aceite continua valendo depois de cada mudança. Pull request pequeno e bem descrito, revisado por outra pessoa com um roteiro, pega o que o teste não cobre: nome confuso, regra esquecida e caso não pensado.

  • 📄 Test Runner nativo — API oficial do Node Escrever e rodar testes com node --test, sem instalar framework.
  • 📄 Pull Request — Martin Fowler O que um pull request resolve, o que ele atrasa e como manter o fluxo andando.
  • 📄 Guia do Autor de Code Review — Google Como escrever descrição de mudança e manter o pull request pequeno.
  • 📄 O Padrão de Revisão — Google O critério para aprovar: a mudança melhora a saúde do código, mesmo sem ser perfeita.

Siga os 10 passos abaixo para construir a prática aplicando os conceitos do bloco:

  1. Configuração do Ambiente: crie api/test/ e acrescente "test": "node --test" nos scripts do package.json.
  2. Separando o App: exporte o app do Express num arquivo e deixe o listen em outro, para o teste subir a API numa porta livre.
  3. Critério Vira Teste: escolha um critério de aceite do ESCOPO.md e escreva o teste com o mesmo Dado, Quando, Então.
  4. Caso de Erro: escreva o teste da regra de negócio principal esperando 409.
  5. Teste de Autenticação: escreva o teste que chama uma rota protegida sem token e espera 401.
  6. Portão na Esteira: acrescente npm test ao job da API no ci.yml, com um serviço PostgreSQL de teste.
  7. Modelo de Pull Request: crie .github/pull_request_template.md com o modelo da atividade 3.
  8. Erro Provocado: abra um PR que altera a validação da regra principal e confirme que o teste barra a mesclagem.
  9. Revisão Cruzada: troque PRs com outra dupla e revise seguindo o roteiro da atividade 3, deixando pelo menos um comentário de pergunta.
  10. Validação e Testes: responda os comentários recebidos, mescle só com a esteira verde e registre no README quantos testes existem e quais critérios eles cobrem.
Concluiu todos os passos?
