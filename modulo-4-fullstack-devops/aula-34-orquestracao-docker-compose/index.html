🧩 1. O compose.yaml: Serviços, Rede e a Aplicação Inteira num Arquivo

🎯 Desafio

A equipe fictícia da Papelaria Ponto Final tem uma API em contêiner e um PostgreSQL que cada pessoa instala de um jeito na própria máquina. Todo novato perde uma manhã com senha errada e porta ocupada antes de rodar o projeto. Como subir API e banco juntos, iguais para todos, com um único comando?

Na aula 32 cada contêiner subia com um docker run cheio de flags. O Compose descreve a aplicação inteira num arquivo: quais serviços existem, como se enxergam na rede e o que cada um recebe de configuração.

  • 📄 Como o Compose funciona — Docker Docs O modelo de aplicação: serviços, redes, volumes e o projeto que o Compose cria a partir do arquivo.
  • 📄 Referência de services — Docker Docs Cada chave que um serviço aceita — image, build, ports, environment, depends_on — com exemplos.
  • 📄 Redes no Compose — Docker Docs Por que o nome do serviço vira endereço dentro da rede e localhost deixa de servir.
  • 📄 Imagem oficial do PostgreSQL — Docker Hub As variáveis POSTGRES_USER, POSTGRES_PASSWORD e POSTGRES_DB e a pasta de dados da imagem.

  • ▶️ Como rodar e customizar o Postgresql com docker e docker-compose Domine AWS com Henrylle Maia · 18:11 — Mostra como subir e configurar um Postgres com docker-compose.

Siga os 10 passos abaixo para construir a prática aplicando os conceitos do bloco:

  1. Configuração do Ambiente: confirme docker compose version e organize a pasta com a API da aula 32 em api/ e um compose.yaml vazio na raiz.
  2. Serviço do Banco: declare o serviço db com image: postgres:16-alpine e as três variáveis POSTGRES_USER, POSTGRES_PASSWORD e POSTGRES_DB.
  3. Serviço da API: declare o serviço api com build: ./api e publique a porta com ports: ["3000:3000"].
  4. Driver do Banco: dentro de api/, rode npm install pg e crie src/db.js com um Pool lendo process.env.DATABASE_URL.
  5. Erro Provocado: passe DATABASE_URL apontando para localhost:5432, suba com docker compose up --build e leia o ECONNREFUSED no log da API.
  6. Ajuste pelo Nome do Serviço: troque localhost por db na URL: dentro da rede do Compose, o nome do serviço é o endereço do contêiner.
  7. Ordem Declarada: acrescente depends_on: [db] na API e registre no README por que isso ainda não garante que o banco aceita conexão.
  8. Tabela na Subida: faça a API criar a tabela tarefas com CREATE TABLE IF NOT EXISTS antes de chamar app.listen.
  9. Comandos do Dia a Dia: use docker compose ps, docker compose logs -f api e docker compose exec db psql -U tarefas e anote o que cada um mostra.
  10. Validação e Testes: crie duas tarefas via POST /tarefas, consulte com SELECT * FROM tarefas no psql, derrube com docker compose down e registre no README o comando único de subida.
Concluiu todos os passos?

💾 2. Volumes, Healthcheck e a Ordem de Subida

🎯 Desafio

Na Papelaria Ponto Final, toda vez que alguém roda docker compose down as tarefas cadastradas somem, e em metade das subidas a API cai porque tentou conectar antes do banco ficar pronto. O time já pensou em colocar um sleep de 10 segundos. Como garantir dado persistente e subida na ordem certa sem adivinhar tempo?

O contêiner do banco é descartável; o dado não pode ser. Volume nomeado guarda o dado fora do ciclo de vida do contêiner, e o healthcheck troca o 'já subiu' pelo 'já aceita conexão'.

  • 📄 Ordem de subida e parada — Docker Docs A diferença entre service_started e service_healthy e como o depends_on usa o healthcheck.
  • 📄 Volumes no Compose — Docker Docs Como declarar volumes nomeados no topo do arquivo e montá-los em cada serviço.
  • 📄 docker compose down — referência da CLI O que o down remove por padrão e o que a opção -v apaga junto.
  • 📄 Bancos de dados em contêiner — Docker Docs O guia oficial de persistência, inicialização e acesso a bancos rodando em contêiner.

Siga os 10 passos abaixo para construir a prática aplicando os conceitos do bloco:

  1. Configuração do Ambiente: suba o projeto da prática anterior, cadastre três tarefas e deixe o terminal de logs aberto.
  2. Provocando a Perda: rode docker compose down seguido de docker compose up e confirme que as tarefas sumiram.
  3. Volume Nomeado: declare volumes: { dados-pg: {} } no topo e monte dados-pg:/var/lib/postgresql/data no serviço db.
  4. Provando a Persistência: repita o ciclo de down e up, confirme que as tarefas ficaram e liste o volume com docker volume ls.
  5. Script de Carga: crie db/init.sql com a tabela e duas tarefas de exemplo e monte em /docker-entrypoint-initdb.d/.
  6. Entendendo o Init: rode docker compose up e observe que o script não executa: ele só roda com a pasta de dados vazia.
  7. Recomeçando do Zero: rode docker compose down -v, suba de novo e confirme no log do banco que o init.sql executou.
  8. Healthcheck do Banco: acrescente um healthcheck com pg_isready -U tarefas -d tarefas, interval: 5s e retries: 10.
  9. Dependência Real: troque o depends_on da API para a forma longa com condition: service_healthy e observe a ordem nos logs.
  10. Validação e Testes: rode docker compose ps e confirme o estado healthy do banco, suba tudo cinco vezes seguidas sem a API cair e registre no README a diferença entre down e down -v.
Concluiu todos os passos?

🎛️ 3. Configuração por Ambiente: .env, Override, Perfis e Watch

🎯 Desafio

A Papelaria Ponto Final quer usar o mesmo projeto em desenvolvimento, com código recarregando sozinho e um painel para olhar o banco, e em produção, sem porta do banco aberta e sem senha escrita no arquivo. Hoje existem dois compose.yaml copiados à mão que já divergem. Como manter um arquivo base e variar só o que muda de um ambiente para outro?

Configuração muda entre ambientes; a descrição da aplicação não. O Compose resolve isso com interpolação de variáveis, arquivos que se sobrepõem, perfis para serviços opcionais e o watch para refletir o código sem rebuild manual.

  • 📄 Variáveis de ambiente no Compose — Docker Docs Como passar variáveis ao contêiner com environment, env_file e interpolação a partir do .env.
  • 📄 Mesclando arquivos Compose — Docker Docs Como o compose.override.yaml é lido automaticamente e como combinar arquivos com -f.
  • 📄 Perfis no Compose — Docker Docs Serviços que só sobem quando o perfil é ativado, como ferramentas de apoio ao desenvolvimento.
  • 📄 Compose Watch — Docker Docs Sincronizar arquivos e reconstruir a imagem automaticamente enquanto você edita o código.

Siga os 10 passos abaixo para construir a prática aplicando os conceitos do bloco:

  1. Configuração do Ambiente: crie .env.example com POSTGRES_PASSWORD=troque-aqui, copie para .env e confirme que .env está no .gitignore.
  2. Interpolação: troque a senha escrita no compose.yaml por ${POSTGRES_PASSWORD:?defina no .env} nos dois serviços.
  3. Erro Provocado: renomeie o .env temporariamente, rode docker compose config e leia a mensagem de variável obrigatória ausente.
  4. Arquivo de Desenvolvimento: crie compose.override.yaml publicando a porta 5432 do banco só em desenvolvimento.
  5. Vendo o Resultado Mesclado: rode docker compose config e confirme que a porta do banco apareceu sem você editar o arquivo base.
  6. Watch no Código: no override, acrescente develop.watch com action: sync para ./api/src e action: rebuild para package.json.
  7. Recarregando Sozinho: suba com docker compose watch, altere uma mensagem da API e confirme a mudança sem rodar build.
  8. Perfil de Ferramentas: no arquivo base, declare o serviço adminer com profiles: ["ferramentas"] e suba com docker compose --profile ferramentas up.
  9. Arquivo de Produção: crie compose.prod.yaml com NODE_ENV: production e restart: unless-stopped e rode docker compose -f compose.yaml -f compose.prod.yaml config.
  10. Validação e Testes: confira que em produção o banco não publica porta e o adminer não sobe, e registre no README os três comandos: desenvolvimento, ferramentas e produção.
Concluiu todos os passos?
