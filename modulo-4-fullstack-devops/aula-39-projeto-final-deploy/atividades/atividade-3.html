Pós-Deploy — Teste de Fumaça, Checagem e Runbook

Aula 39 · Módulo 4: Fullstack, DevOps e Projeto Final · ByteClass

O que esta atividade entrega

O script de teste de fumaça, o workflow que o executa a cada 30 minutos, o runbook de reversão e o modelo de análise pós-incidente.

scripts/fumaca.sh

#!/usr/bin/env bash
# Início: fumaca.sh — confere em segundos se a produção está respondendo
set -euo pipefail

API_URL="${API_URL:?defina API_URL}"
FRONT_URL="${FRONT_URL:?defina FRONT_URL}"

curl -fsS --max-time 60 "$API_URL/saude/pronto" > /dev/null && echo "API pronta"
curl -fsS --max-time 30 "$FRONT_URL" > /dev/null && echo "Frontend no ar"
curl -fsS --max-time 30 "$API_URL/horarios-livres?data=$(date +%F)" > /dev/null && echo "Consulta pública ok"

echo "Teste de fumaça concluído"
# Fim de fumaca.sh

.github/workflows/checagem.yml

# Início: checagem.yml — roda o teste de fumaça contra a produção a cada 30 minutos
name: Checagem de produção

on:
  schedule:
    - cron: "*/30 * * * *"
  workflow_dispatch:

jobs:
  fumaca:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: bash scripts/fumaca.sh
        env:
          API_URL: ${{ vars.API_URL }}
          FRONT_URL: ${{ vars.FRONT_URL }}
# Fim de checagem.yml

docs/RUNBOOK.md

<!-- Início: RUNBOOK.md — o que fazer quando a produção da Agenda Lírio quebrar -->
# Runbook — Agenda Lírio

## 1. Confirmar
- Rode `scripts/fumaca.sh` e anote qual verificação falhou.
- Abra o log da API no painel do Render e procure linhas com level de erro.

## 2. Decidir: corrigir ou voltar
- O problema começou logo após um deploy? Volte primeiro, investigue depois.
- O problema é de configuração (variável, senha)? Corrija a variável no painel.

## 3. Voltar a versão
- Render: Events › escolher o deploy anterior › Rollback.
- Vercel: Deployments › deploy anterior › Promote to Production.
- Rode o teste de fumaça de novo.

## 4. Comunicar
- Avise o Studio Lírio: o que parou, desde quando e a previsão de volta.

## 5. Registrar
- Preencha a análise pós-incidente em até 48 horas.

# Incidente — login indisponível

- Início: sábado, 10h05 (primeira checagem vermelha)
- Detecção: checagem agendada do GitHub Actions
- Fim: sábado, 10h21 (checagem verde após correção)
- Impacto: recepção sem acesso por 16 minutos

## Linha do tempo
- 10h00 — senha do banco trocada no painel do Neon
- 10h05 — checagem falha em /saude/pronto
- 10h12 — log mostra falha de autenticação no banco
- 10h19 — DATABASE_URL atualizada no Render

## Causa
A senha do banco foi trocada sem atualizar a variável da API.

## O que funcionou
A checagem agendada avisou antes de qualquer usuário.

## Ações
- [ ] Incluir no runbook: troca de senha do banco exige atualizar DATABASE_URL no mesmo momento.

O que observar

  • O --max-time 60 na primeira chamada dá tempo para a API acordar da hibernação do plano gratuito.
  • As URLs ficam em variáveis do repositório (vars), não em segredo: elas são públicas; o que importa é não repeti-las no código.
  • A análise descreve o que aconteceu com o sistema e o processo, não quem errou.
