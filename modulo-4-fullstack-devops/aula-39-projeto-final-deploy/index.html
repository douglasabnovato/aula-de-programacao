🧾 1. Preparando o Projeto para Produção

🎯 Desafio

A Agenda Lírio roda perfeita no Compose, mas a API tem a porta 3000 escrita no código, o CORS libera qualquer origem, a mensagem de erro devolve a pilha inteira e a URL do banco só funciona sem SSL. A dona do Studio Lírio quer começar a usar na segunda-feira. O que precisa mudar no código antes de ele sair da sua máquina?

Produção é outro ambiente com as mesmas regras: configuração vem de variável, serviços de apoio são endereços trocáveis e nada que ajuda a depurar pode vazar para o usuário. A preparação é uma lista verificável, não uma sensação.

  • 📄 Twelve-Factor — Paridade entre Desenvolvimento e Produção Por que manter desenvolvimento e produção o mais parecidos possível reduz surpresa no deploy.
  • 📄 Twelve-Factor — Vínculo de Portas A aplicação exporta o serviço numa porta que o ambiente define, não numa porta escrita no código.
  • 📄 Twelve-Factor — Serviços de Apoio O banco como recurso anexado por URL, trocável sem mudar código.
  • 📄 Helmet — documentação oficial Os cabeçalhos de segurança HTTP que o Express passa a enviar com uma linha.

  • ▶️ Node.js API [C07P03] - Producionalização - Boas práticas em erros de API Waldemar Neto - Dev Lab · 25:59 — Apresenta boas práticas de tratamento de erros ao preparar uma API Node.js para produção.

Siga os 10 passos abaixo para construir a prática aplicando os conceitos do bloco:

  1. Configuração do Ambiente: crie a branch preparo-producao e abra o checklist da atividade 1 ao lado do código.
  2. Porta do Ambiente: troque a porta fixa por process.env.PORT com valor padrão só para desenvolvimento.
  3. Banco por URL: leia a conexão só de DATABASE_URL e ative SSL quando NODE_ENV for production.
  4. Origem Restrita: configure o CORS com a origem de process.env.ORIGEM_FRONT, sem *.
  5. Cabeçalhos de Segurança: rode npm install helmet e registre app.use(helmet()) antes das rotas.
  6. Erro Provocado: com NODE_ENV=production, force um erro numa rota e observe se a resposta ainda traz a pilha e o caminho dos arquivos.
  7. Erro sem Vazamento: no middleware de erro, devolva só a mensagem genérica e o requestId, mantendo a pilha apenas no log.
  8. Scripts de Produção: confira que existem npm start sem ferramentas de desenvolvimento e npm run migrar para rodar as migrações.
  9. Configuração Completa: revise os .env.example da API e do frontend para listar toda variável que a produção precisa.
  10. Validação e Testes: suba localmente com NODE_ENV=production e as variáveis de produção simuladas, marque cada item do checklist e registre no README o que precisou ser alterado.
Concluiu todos os passos?

🚀 2. Deploy em Hospedagem Gratuita: Banco, API e Frontend

🎯 Desafio

O Studio Lírio não tem orçamento para servidor, e a Agenda Lírio precisa estar num endereço público para a banca e para a recepção testarem. São três partes para publicar, cada uma num serviço diferente, e a primeira tentativa do time terminou com o frontend no ar chamando localhost. Em que ordem publicar cada parte, e como ligar uma à outra sem pagar nada?

Cada parte tem um tipo de hospedagem: banco gerenciado, serviço web para a API e hospedagem estática para o frontend. A ordem importa porque cada parte precisa do endereço da anterior, e o frontend recebe a URL da API no momento do build.

  • 📄 Vite — Construindo para Produção O que o build gera e como a pasta de saída é servida por uma hospedagem estática.
  • 📄 Vite — Variáveis de Ambiente e Modos Por que a URL da API entra no build e precisa estar configurada no provedor antes dele.
  • 📄 Twelve-Factor — Descartabilidade Processo que inicia rápido e encerra com elegância, o que importa quando o plano gratuito hiberna a API.
  • 📄 Criando um site no GitHub Pages — GitHub A alternativa gratuita de hospedagem estática direto do repositório.

Siga os 10 passos abaixo para construir a prática aplicando os conceitos do bloco:

  1. Configuração do Ambiente: crie contas gratuitas no Neon (ou Supabase), no Render e na Vercel (ou Netlify), todas ligadas à sua conta do GitHub.
  2. Banco Primeiro: crie o projeto PostgreSQL no plano free, copie a connection string e guarde-a só no gerenciador de senhas, nunca no repositório.
  3. Migrações em Produção: rode npm run migrar da sua máquina com DATABASE_URL apontando para o banco de produção e confira as tabelas no painel.
  4. API no Render: crie um Web Service no plano free apontando para a pasta api/, com npm ci como build e npm start como início.
  5. Variáveis da API: cadastre no painel do Render DATABASE_URL, JWT_SECRET, NODE_ENV=production e ORIGEM_FRONT provisória.
  6. Health Check: configure o caminho /saude/pronto como health check e acompanhe o primeiro deploy pelo log do painel.
  7. Erro Provocado: publique o frontend na Vercel sem definir VITE_API_URL e veja no DevTools as chamadas indo para localhost.
  8. Frontend Ligado: defina VITE_API_URL com a URL pública da API, refaça o deploy e confirme a nova URL no JS gerado.
  9. Fechando o CORS: troque ORIGEM_FRONT no Render pela URL definitiva do frontend e aguarde a API reiniciar.
  10. Validação e Testes: percorra o fluxo completo num celular pela rede móvel, meça o tempo da primeira requisição depois de 20 minutos parado e registre na ficha de deploy as três URLs e esse tempo.

🩺 3. Pós-Deploy: Verificação, Monitoramento e Plano de Volta

🎯 Desafio

A Agenda Lírio foi publicada na sexta e na segunda a recepção avisou que o login não funcionava desde sábado. O time só soube pelo telefone, e ninguém sabia se o certo era corrigir às pressas ou voltar a versão anterior. Como saber em minutos que a produção quebrou e ter o caminho de volta escrito antes de precisar dele?

Publicar não termina o trabalho. Um teste de fumaça logo após cada deploy, uma checagem periódica do endereço público e um runbook com o passo de reversão transformam o incidente de pânico em procedimento.

  • 📄 Release Engineering — Google SRE Publicação repetível e reversível como parte do processo, não como evento.
  • 📄 Managing Incidents — Google SRE Papéis, comunicação e registro durante um incidente, mesmo num time pequeno.
  • 📄 Postmortem Culture — Google SRE Como escrever a análise pós-incidente sem culpados e com ações que evitam a repetição.
  • 📄 Error Handling Cheat Sheet — OWASP Tratar erro em produção sem expor detalhe interno ao usuário.

Siga os 10 passos abaixo para construir a prática aplicando os conceitos do bloco:

  1. Configuração do Ambiente: crie scripts/fumaca.sh e docs/RUNBOOK.md no repositório do projeto.
  2. Teste de Fumaça: no script, chame com curl -f o /saude/pronto, a página inicial do frontend e a rota pública de consulta.
  3. Rodando após o Deploy: execute o script contra as URLs de produção e confirme que ele termina com código de saída 0.
  4. Checagem Agendada: crie um workflow no GitHub Actions com gatilho schedule a cada 30 minutos rodando o mesmo script.
  5. Aviso de Falha: configure o repositório para que a falha do workflow gere notificação por e-mail para o time.
  6. Erro Provocado: troque a senha do banco no painel sem atualizar a DATABASE_URL no Render e acompanhe a checagem ficar vermelha.
  7. Reversão: use o botão de voltar a um deploy anterior no painel do Render e cronometre até a checagem voltar ao verde.
  8. Runbook: escreva no RUNBOOK.md como diagnosticar, reverter e comunicar, com os links dos três painéis.
  9. Pós-Incidente: preencha o modelo de análise da atividade 3 para o incidente provocado.
  10. Validação e Testes: peça a um colega que siga só o runbook para reverter um deploy e registre no README o tempo total e o que ele precisou perguntar.
Concluiu todos os passos?
