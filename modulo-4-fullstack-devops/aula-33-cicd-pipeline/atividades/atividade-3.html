Deploy Condicional e Plano de Reversão

Aula 33 · Módulo 4: Fullstack, DevOps e Projeto Final · ByteClass

Job de deploy, dependente dos portões

  publicar:
    needs: [lint, teste]
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: '20', cache: 'npm' }
      - run: npm ci
      - run: npm run build
        env:
          VITE_API_URL: ${{ secrets.API_URL_PRODUCAO }}
      - name: Publicar no GitHub Pages
        uses: peaceiris/actions-gh-pages@v4
        with:
          github_token: ${{ secrets.GITHUB_TOKEN }}
          publish_dir: ./dist

As duas linhas que evitam acidente

  • needs: [lint, teste] — não publica se algum portão falhou.
  • if: github.ref == 'refs/heads/main' — branch de trabalho não vai para produção.

Segredo: como o GitHub protege

# No workflow você escreve:
env:
  TOKEN: ${{ secrets.TOKEN_DEPLOY }}

# No log da execução aparece:
TOKEN: ***

O mascaramento é automático. Mas ele só cobre o valor exato do segredo — se o seu código imprimir o token em pedaços ou codificado, ele vaza. Não imprima.

O plano de reversão, escrito antes de precisar

# 1. Identificar o commit que quebrou
git log --oneline -5

# 2. Reverter (cria um commit novo que desfaz, sem reescrever histórico)
git revert <hash>

# 3. Enviar
git push origin main

# 4. A esteira republica sozinha a versão anterior

Meça, não estime

Cronometre de verdade quanto tempo leva do git revert até o site voltar ao ar. Esse número — e não a confiança da equipe — é o que diz se vocês podem publicar automaticamente. Se for mais de dez minutos, o risco de publicar direto é alto demais.
