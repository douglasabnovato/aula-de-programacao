🔁 1. Integração Contínua: o que é e o que não é

CI não é ter um arquivo YAML no repositório. É a prática de integrar cedo e com frequência, com uma verificação automática que dá o veredito em minutos.

  • 📄 Continuous Integration — Martin Fowler O artigo de referência que define a prática, com as condições que precisam existir.
  • 📄 Entendendo o GitHub Actions Os conceitos de workflow, job, step e runner, na documentação oficial em português.
  • 📄 Deployment Pipeline — Martin Fowler Por que a esteira é organizada em estágios e o que cada um deve provar.
  • 📄 GitHub Actions — Início Rápido O menor workflow possível, para ver a esteira rodando em cinco minutos.

🎥 Curadoria de vídeo pendente. Este bloco recebe os vídeos de apoio selecionados pelo instrutor para o tema acima.

Siga os 10 passos abaixo para construir a prática aplicando os conceitos do bloco:

  1. Configuração do Ambiente: confirme que o projeto da API está num repositório no GitHub.
  2. Criando a Pasta: crie .github/workflows/ na raiz do repositório.
  3. Arquivo do Workflow: crie ci.yml com um nome descritivo no campo name.
  4. Definindo o Gatilho: configure on: [push, pull_request] para disparar nos dois casos.
  5. Escolhendo o Runner: declare runs-on: ubuntu-latest no job.
  6. Baixando o Código: use a ação actions/checkout@v4 como primeiro passo.
  7. Preparando o Node: use actions/setup-node@v4 fixando a versão 20.
  8. Instalando: rode npm ci — não npm install — para instalação reproduzível.
  9. Disparando: faça commit e push, e acompanhe a execução na aba Actions.
  10. Validação e Testes: quebre o código de propósito, faça push e confirme que a esteira ficou vermelha.

🧪 2. Os Portões de Qualidade da Esteira

Uma esteira que só instala dependência não protege ninguém. Os portões são o que fazem o commit ruim parar antes do usuário: lint, teste, build e auditoria.

  • 📄 Test Runner nativo do Node O executor de testes que vem junto com o Node, sem instalar nada.
  • 📄 Jobs em um Workflow — GitHub Como paralelizar e encadear etapas, e o que o needs faz.
  • 📄 npm audit — documentação oficial Como a checagem de vulnerabilidade funciona e como interpretar o relatório.
  • 📄 ESLint — primeiros passos Configuração mínima do linter e integração com a esteira.

🎥 Curadoria de vídeo pendente. Este bloco recebe os vídeos de apoio selecionados pelo instrutor para o tema acima.

Siga os 10 passos abaixo para construir a prática aplicando os conceitos do bloco:

  1. Configuração do Ambiente: crie a pasta test na API e um arquivo tarefas.test.js.
  2. Primeiro Teste: use o test runner nativo para verificar que criar tarefa sem título lança erro.
  3. Script de Teste: acrescente \"test\": \"node --test\" nos scripts do package.json.
  4. Rodando Local: execute npm test e confirme que passa antes de levar para a esteira.
  5. Portão de Teste: acrescente o passo npm test no workflow, depois do npm ci.
  6. Portão de Lint: instale o ESLint, configure e acrescente npm run lint à esteira.
  7. Portão de Auditoria: acrescente npm audit --audit-level=high como passo.
  8. Separando em Jobs: divida lint e teste em dois jobs para rodarem em paralelo.
  9. Provando o Portão: escreva um teste que falha de propósito e confirme que a esteira barra.
  10. Validação e Testes: abra um Pull Request e confirme que o GitHub mostra o resultado dos portões nele.

🎯 3. Implantação Automática e o Direito de Voltar Atrás

Publicar automático só é seguro quando voltar atrás também é rápido. O bloco fecha com a etapa de deploy, os segredos fora do código e o plano de reversão.

  • 📄 Segredos no GitHub Actions Como armazenar e usar credenciais sem que apareçam no log da execução.
  • 📄 Condições de Execução — GitHub Actions O if que faz o deploy rodar só no branch principal.
  • 📄 Publicando com GitHub Pages Configurar a origem de publicação e o deploy por Actions.
  • 📄 Google SRE — Engenharia de Release O capítulo gratuito sobre publicar com segurança e reverter rápido.

🎥 Curadoria de vídeo pendente. Este bloco recebe os vídeos de apoio selecionados pelo instrutor para o tema acima.

Siga os 10 passos abaixo para construir a prática aplicando os conceitos do bloco:

  1. Configuração do Ambiente: em Settings › Secrets, crie um segredo de teste chamado TOKEN_DEPLOY.
  2. Job de Deploy: acrescente um segundo job com needs: [teste, lint] para depender dos portões.
  3. Condição de Branch: use if: github.ref == 'refs/heads/main' para publicar só do principal.
  4. Usando o Segredo: leia com ${{ secrets.TOKEN_DEPLOY }} e confirme que o log mostra apenas asteriscos.
  5. Passo de Build: rode o build do frontend dentro do job de deploy.
  6. Publicando: configure a publicação no GitHub Pages a partir do artefato gerado.
  7. Marcando a Versão: crie uma tag Git a cada publicação bem-sucedida.
  8. Ensaiando a Volta: pratique git revert do último commit e veja a esteira republicar a versão anterior.
  9. Medindo o Tempo: cronometre quanto leva do revert até o site voltar ao ar.
  10. Validação e Testes: registre no README o tempo medido e o passo a passo de reversão de emergência.
Concluiu todos os passos?
