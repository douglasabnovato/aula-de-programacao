🧭 1. Monolito, Microsserviços e Onde Cortar

🎯 Desafio

O Armazém Serra Verde, uma loja fictícia de produtos naturais, tem uma API única que cuida de pedidos e manda e-mail de confirmação. Quando o provedor de e-mail fica lento, o cadastro de pedidos inteiro trava junto, e o time quer dividir tudo em dez serviços de uma vez. Qual parte vale separar primeiro, e como saber se separar resolve ou só espalha o problema?

Microsserviço é uma escolha de arquitetura com custo: rede no meio, deploy independente, dado separado. Antes de dividir, é preciso achar a fronteira que tem motivo próprio para mudar e falhar sozinha.

  • 📄 Microservices — James Lewis e Martin Fowler O artigo que definiu o termo: serviços organizados por capacidade de negócio, com dado e deploy próprios.
  • 📄 Monolith First — Martin Fowler Por que começar com um monolito bem dividido e só extrair serviços quando a fronteira ficar clara.
  • 📄 Microservice Prerequisites — Martin Fowler O mínimo que precisa existir antes: provisionamento rápido, monitoramento e deploy automatizado.
  • 📄 Microservice Trade-Offs — Martin Fowler Os ganhos e as perdas lado a lado, incluindo consistência eventual e complexidade operacional.

Siga os 10 passos abaixo para construir a prática aplicando os conceitos do bloco:

  1. Configuração do Ambiente: crie a pasta serra-verde/ com duas subpastas, pedidos/ e notificacoes/, cada uma com seu package.json e Dockerfile.
  2. Mapa de Responsabilidades: liste num ARQUITETURA.md o que a API atual faz e marque o que muda por motivo diferente de pedido: o envio de aviso.
  3. Decisão de Fronteira: registre no mesmo arquivo por que notificação é a primeira extração: falha sozinha, muda sozinha e não precisa do banco de pedidos.
  4. Serviço de Notificações: em notificacoes/server.js, crie POST /notificacoes que valida pedidoId e cliente e responde 201.
  5. Serviço de Pedidos: em pedidos/server.js, crie POST /pedidos que guarda o pedido e chama o outro serviço com fetch.
  6. Endereço por Configuração: leia a URL do outro serviço de process.env.NOTIFICACOES_URL em vez de escrever o endereço no código.
  7. Compose com Dois Serviços: declare pedidos com porta publicada e notificacoes sem porta publicada, só acessível pela rede interna.
  8. Erro Provocado: defina NOTIFICACOES_URL=http://localhost:4001, crie um pedido e leia o erro de conexão: dentro do contêiner, localhost é ele mesmo.
  9. Ajuste: troque para http://notificacoes:4001, suba de novo e acompanhe as duas linhas de log, uma em cada serviço.
  10. Validação e Testes: crie três pedidos, consulte GET /notificacoes pelo docker compose exec e registre no README o custo novo que a divisão trouxe: uma chamada de rede que pode falhar.
Concluiu todos os passos?

🔌 2. Comunicação entre Serviços e Falhas Parciais

🎯 Desafio

No Armazém Serra Verde, o serviço de notificações ficou fora do ar por dez minutos e cada novo pedido esperou 30 segundos antes de devolver erro 500. O cliente pagou, mas viu uma tela de falha e tentou de novo, gerando pedido duplicado. Como fazer o serviço de pedidos continuar funcionando quando a dependência cai?

Numa chamada de rede, a pergunta não é se vai falhar, mas o que acontece quando falhar. Tempo máximo de espera, nova tentativa com intervalo crescente e disjuntor são as peças que isolam a falha de um serviço dos demais.

  • 📄 Circuit Breaker — Martin Fowler O padrão do disjuntor explicado com código: fechado, aberto e meio-aberto.
  • 📄 Padrão Retry — Microsoft Learn Quando repetir uma chamada ajuda, quando piora, e por que o intervalo deve crescer.
  • 📄 Padrão Circuit Breaker — Microsoft Learn A máquina de estados do disjuntor e como ela convive com o retry.
  • 📄 AbortSignal.timeout() — MDN Como limitar o tempo de um fetch sem escrever setTimeout e AbortController à mão.

Siga os 10 passos abaixo para construir a prática aplicando os conceitos do bloco:

  1. Configuração do Ambiente: suba o projeto da prática anterior e crie pedidos/src/clienteNotificacoes.js para concentrar a chamada de rede.
  2. Simulando Lentidão: no serviço de notificações, leia ATRASO_MS do ambiente e espere esse tempo antes de responder.
  3. Erro Provocado: suba com ATRASO_MS=30000, crie um pedido e cronometre quanto tempo o cliente fica esperando.
  4. Tempo Máximo: passe signal: AbortSignal.timeout(2000) no fetch e confirme que a espera cai para dois segundos.
  5. Nova Tentativa: envolva a chamada num laço de até três tentativas com espera de 200 * 2 ** (tentativa - 1) milissegundos.
  6. Só o que Vale Repetir: repita apenas em falha de rede e status 5xx; um 400 não melhora na segunda tentativa.
  7. Disjuntor: guarde o número de falhas seguidas e abra o disjuntor na terceira, recusando chamadas por 15 segundos.
  8. Resposta Degradada: quando a notificação falhar, responda 201 com o pedido e notificacao: "pendente" em vez de 500.
  9. Estado Visível: crie GET /saude/dependencias devolvendo o estado atual do disjuntor.
  10. Validação e Testes: pare o contêiner de notificações com docker compose stop notificacoes, crie pedidos, acompanhe o disjuntor abrir e fechar ao religar o serviço e registre os tempos no README.

📈 3. Escalando na Horizontal sem Estado no Processo

🎯 Desafio

Na semana de promoção, o Armazém Serra Verde subiu três cópias da API atrás de um balanceador. O contador de visitas da página começou a mostrar números diferentes a cada recarga e alguns clientes perderam o carrinho no meio da compra. O que precisa sair de dentro do processo para que três cópias se comportem como uma só?

Escalar na horizontal é rodar mais cópias do mesmo processo. Isso só funciona se nenhuma cópia guardar estado que as outras precisem: sessão, contador e carrinho vão para um serviço de apoio compartilhado.

  • 📄 Twelve-Factor — Processos Por que processos devem ser sem estado e compartilhar nada entre si.
  • 📄 Twelve-Factor — Concorrência Escalar pelo modelo de processos: mais cópias em vez de uma máquina maior.
  • 📄 Nginx como balanceador HTTP — nginx.org Como o bloco upstream distribui requisições entre servidores e quais métodos existem.
  • 📄 docker compose scale — referência da CLI Como mudar o número de réplicas de um serviço do Compose.

Siga os 10 passos abaixo para construir a prática aplicando os conceitos do bloco:

  1. Configuração do Ambiente: crie a pasta vitrine/ com api/server.js, um nginx.conf e um compose.yaml.
  2. Identificando a Réplica: crie GET /visitas devolvendo os.hostname() para saber qual cópia respondeu.
  3. Contador em Memória: guarde as visitas numa variável let total = 0 e devolva o valor a cada chamada.
  4. Balanceador: no nginx.conf, declare upstream api_replicas { server api:3000; } e um proxy_pass para ele.
  5. Réplicas: no Compose, deixe a API sem ports e acrescente deploy: { replicas: 3 }; publique só a porta 8080 do Nginx.
  6. Erro Provocado: chame /visitas dez vezes e observe o hostname alternando e o total voltando para trás: cada réplica tem o seu.
  7. Serviço de Apoio: acrescente o serviço redis com image: redis:7-alpine e instale npm install redis na API.
  8. Estado Compartilhado: troque a variável por await redis.incr('visitas') e conecte ao Redis antes do app.listen.
  9. Mudando a Escala: rode docker compose up -d --scale api=5 e reinicie o Nginx para ele enxergar as novas réplicas.
  10. Validação e Testes: chame /visitas vinte vezes, confirme hostnames diferentes com total sempre crescente e registre no README o que mais na sua API guarda estado em memória.
Concluiu todos os passos?
