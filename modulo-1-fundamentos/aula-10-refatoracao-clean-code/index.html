🏷️ 1. Nomes que Explicam e Funções Pequenas

🎯 Desafio

O script de pedidos da loja fictícia Casa do Tempero tem uma função chamada f, com variáveis x, y e tmp, que, num bloco só, calcula subtotal, desconto, frete e ainda monta a mensagem da tela. Funciona, mas ninguém tem coragem de mexer quando a regra de desconto muda. Como reescrever para que o código diga o que faz sem precisar de comentário, mantendo exatamente o mesmo resultado?

Código é lido muito mais vezes do que escrito. Nomes que revelam intenção e funções que fazem uma coisa só reduzem o tempo que alguém leva para entender e alterar um trecho. Renomear, extrair variável e extrair função são as refatorações mais usadas no dia a dia.

  • 📄 Rename Method — Refactoring.Guru Quando o nome não diz o que a função faz, e como renomear com segurança.
  • 📄 Extract Variable — Refactoring.Guru Dar nome a uma expressão complicada para ela se explicar sozinha.
  • 📄 Extract Method — Refactoring.Guru Separar um trecho de uma função longa numa função nova com nome claro.
  • 📄 JavaScript code guidelines — MDN As convenções que a própria MDN usa para nomes, funções e estilo em JavaScript.

Siga os 10 passos abaixo para construir a prática aplicando os conceitos do bloco:

  1. Configuração do Ambiente: crie a pasta aula-10-nomes com os três arquivos e cole a função f original num bloco separado do código.
  2. Entendendo Antes de Mexer: rode f com três pedidos diferentes e anote as entradas e saídas no README: esse é o comportamento a preservar.
  3. Renomeando a Função: troque f por resumirPedido e cada variável de uma letra por um nome do negócio, como subtotal e desconto.
  4. Extraindo Variáveis: transforme a condição x > 200 && c em const ganhaDescontoFidelidade.
  5. Extraindo a Primeira Função: mova o cálculo do desconto para calcularDesconto(subtotal, clienteFiel).
  6. Extraindo as Demais: faça o mesmo com calcularFrete(subtotal, cidade) e formatarMensagem(resumo).
  7. Erro Provocado: ao extrair o frete, esqueça de passar cidade como parâmetro e observe o ReferenceError.
  8. Uma Coisa por Função: confira que nenhuma função nova mistura cálculo com montagem de texto.
  9. Comparando com a Original: para cada pedido do passo 2, compare o resultado de f e de resumirPedido.
  10. Validação e Testes: confirme que os resultados são idênticos e registre no README o antes e depois de cada nome.

♻️ 2. Duplicação e Números Mágicos

🎯 Desafio

No sistema de ingressos fictício do Cine Largo, o desconto da meia-entrada (50%) e a taxa de conveniência (R$ 3,50) aparecem digitados em vários lugares do código. Quando a taxa subiu, só parte dos lugares foi atualizada e dois tipos de ingresso ficaram com o preço antigo. Como fazer cada regra de negócio morar num lugar só?

Número mágico é um valor solto no código cujo significado só o autor conhece. Duplicação é a mesma regra escrita mais de uma vez. As duas coisas fazem uma mudança de regra exigir caça ao tesouro. Constantes com nome e dados que descrevem as variações substituem blocos de if copiados.

  • 📄 Replace Magic Number with Symbolic Constant — Refactoring.Guru Trocar um número solto por uma constante que explica o que ele significa.
  • 📄 Long Method — Refactoring.Guru O sinal de que uma função está fazendo coisas demais e como quebrá-la.
  • 📄 Code Smells — Refactoring.Guru O catálogo de sinais de problema no código, agrupados por categoria.

Siga os 10 passos abaixo para construir a prática aplicando os conceitos do bloco:

  1. Configuração do Ambiente: crie a pasta aula-10-ingressos com os três arquivos e uma tabela vazia de tipos de ingresso.
  2. Mapeando a Duplicação: na versão original com if/else, marque no README cada lugar onde 0.5, 3.5 e 28 aparecem.
  3. Constantes com Nome: crie const REGRAS = Object.freeze({ PRECO_BASE: 28, TAXA_CONVENIENCIA: 3.5, ... }).
  4. Dados em Vez de if: descreva cada tipo de ingresso num array { id, nome, fator } em vez de um if por tipo.
  5. Uma Função de Preço: crie precoDoIngresso(tipo, regras) que usa só o fator do tipo e as constantes.
  6. Erro Provocado: mude a taxa só num if da versão antiga e compare os preços com a nova versão.
  7. Regra Editável: ligue um campo de taxa da tela a uma cópia das regras e recalcule toda a tabela ao mudar o valor.
  8. Novo Tipo Sem Código Novo: adicione o tipo 'Professor' só incluindo um objeto no array.
  9. Nomes e Formatação: extraia formatarMoeda e garanta que nenhum número solto sobrou fora de REGRAS.
  10. Validação e Testes: altere a taxa e confirme que todos os tipos mudaram juntos; registre no README quantos lugares a regra ocupa agora.

🛡️ 3. Refatoração Segura: Testes Antes, Passos Pequenos e Responsabilidades

🎯 Desafio

A equipe do app fictício Placar Amador quer reorganizar o arquivo único que calcula a tabela do campeonato do bairro. Da última vez que alguém 'limpou' esse código, o empate passou a valer zero ponto e ninguém percebeu por uma semana. Como mudar a estrutura sem mudar o comportamento — e provar isso?

Refatorar é mudar a estrutura interna sem mudar o comportamento observável. Para isso ser verdade, o comportamento precisa estar protegido por testes antes da primeira alteração, e cada passo precisa ser pequeno o bastante para ser desfeito. Separar dados, regras e interface deixa cada parte testável.

  • 📄 Definition Of Refactoring — Martin Fowler A definição de quem cunhou o termo: estrutura muda, comportamento não.
  • 📄 How to refactor — Refactoring.Guru O checklist: código mais limpo, sem funcionalidade nova e com todos os testes passando.
  • 📄 Opportunistic Refactoring — Martin Fowler Refatorar um pouco a cada visita ao código, em vez de esperar um grande momento.
  • 📄 JavaScript modules — MDN O próximo passo da organização: separar dados, regras e interface em arquivos com import e export.

Siga os 10 passos abaixo para construir a prática aplicando os conceitos do bloco:

  1. Configuração do Ambiente: crie a pasta aula-10-placar com os três arquivos e uma lista de jogos de exemplo em array.
  2. Testes de Caracterização: antes de mexer, escreva testes que registram o resultado atual: pontos, saldo e ordem de três times.
  3. Rodando a Base: rode os testes e confirme que todos passam com o código original.
  4. Separando os Dados: agrupe no topo do arquivo os jogos e as constantes PONTOS_VITORIA e PONTOS_EMPATE.
  5. Separando as Regras: extraia calcularTabela(jogos, pontos) como função pura, sem acessar o DOM.
  6. Separando a Interface: deixe renderizarTabela(tabela) como a única função que escreve no HTML.
  7. Um Passo de Cada Vez: rode os testes depois de cada extração; se algum falhar, desfaça só o último passo.
  8. Erro Provocado: simule uma 'limpeza' que troca o empate para 0 ponto e veja quais testes denunciam a mudança.
  9. Critério de Desempate: extraia compararTimes(a, b) com pontos, vitórias e saldo, e confirme a ordem com os testes.
  10. Validação e Testes: rode a suíte final, anote no README a estrutura antes e depois e em que ordem você fez os passos.
