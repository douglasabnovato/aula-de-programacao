🐞 1. Depuração com DevTools: Console, Breakpoints e debugger

🎯 Desafio

Na calculadora de frete fictícia da loja Rota Verde, um pedido de R$ 30 com frete de R$ 10 mostra total de 'R$ 3010'. Nenhum erro aparece no console e o código parece certo à primeira vista. Como descobrir em que linha o valor sai errado sem encher o arquivo de console.log às cegas?

Depurar é observar o programa rodando em vez de adivinhar. O DevTools permite pausar a execução numa linha (breakpoint ou a instrução debugger), inspecionar o valor e o tipo de cada variável naquele instante e avançar passo a passo até o ponto em que o dado muda de forma inesperada.

  • 📄 Pause your code with breakpoints — Chrome DevTools Os tipos de breakpoint: de linha, condicional, de evento e de exceção.
  • 📄 Console overview — Chrome DevTools O console como lugar para testar expressões com o código pausado.
  • 📄 JavaScript debugging and error handling — MDN Learn Tipos de erro, como ler a mensagem do console e estratégias de investigação.

  1. Configuração do Ambiente: crie a pasta aula-9-frete com os três arquivos e um formulário com preço, quantidade e frete.
  2. Reproduzindo o Bug: preencha preço 10, quantidade 3 e frete 10, e anote no README o resultado esperado e o obtido.

  7. A Instrução debugger: marque o checkbox 'pausar com debugger' e veja a execução parar sozinha com o DevTools aberto.

  9. Corrigindo na Origem: converta os campos com Number(...) no momento da leitura e remova o debugger.
  10. Validação e Testes: repita o cenário do passo 2, teste valores decimais e registre no README a causa e a correção do bug.

✅ 2. Testes Unitários no Navegador com Asserções

🎯 Desafio

A escola fictícia Nota Dez calcula a média final e a situação de cada aluno — aprovado, recuperação ou reprovado — com duas funções. Ontem alguém trocou um >= por > e os alunos com média exatamente 7 foram para a recuperação sem ninguém perceber. Como detectar esse tipo de mudança em segundos, antes de publicar?

Um teste unitário chama uma função com uma entrada conhecida e confere se a saída é a esperada. Funções puras, que só dependem dos parâmetros, são as mais fáceis de testar. Frameworks como Jest organizam isso em describe, test e expect; aqui o mesmo formato é construído à mão para entender o que eles fazem por baixo.

  • 📄 Getting Started — Jest O formato test/expect que a prática imita e que o aluno usará no Módulo 3.
  • 📄 Using Matchers — Jest toBe, toEqual e outros comparadores, e quando usar cada um.

Siga os 10 passos abaixo para construir a prática aplicando os conceitos do bloco:

  1. Configuração do Ambiente: crie a pasta aula-9-testes com os três arquivos e uma lista vazia para os resultados.
  2. Funções Puras: escreva calcularMedia(notas) e situacao(media) sem ler nada do DOM dentro delas.

🧯 3. Tratamento de Erros: throw, try/catch e Mensagens Úteis

🎯 Desafio

O formulário de inscrição fictício da Semana Tech Serra Azul aceita idade 'abc' e e-mail vazio. O problema só aparece depois, no meio do processamento, como 'Cannot read properties of undefined', e o participante não entende o que fazer. Como recusar dados inválidos no ponto de entrada, com uma mensagem que a pessoa entenda, sem esconder os erros de programação?

Nem todo erro é igual: dado inválido do usuário é esperado e merece uma mensagem clara; erro de programação precisa aparecer para quem desenvolve. throw interrompe o fluxo com um objeto Error, try/catch decide onde tratar, e uma classe de erro própria permite separar os dois casos com instanceof.

  • 📄 Control flow and error handling — MDN Visão geral de fluxo de controle e tratamento de exceções na linguagem.

Siga os 10 passos abaixo para construir a prática aplicando os conceitos do bloco:

  1. Configuração do Ambiente: crie a pasta aula-9-inscricao com os três arquivos e um formulário com nome, e-mail e idade.
  2. Erro Provocado: processe a inscrição sem validar, com idade 'abc', e leia o resultado estranho que chega ao final.
  3. Classe de Erro Própria: crie class ErroValidacao extends Error com um campo campo para indicar onde está o problema.
  4. Validando na Entrada: crie validarInscricao(dados) que lança new ErroValidacao(...) para cada regra violada.
  5. Mensagens para Pessoas: escreva mensagens que digam o que corrigir, como 'Informe a idade em números, entre 14 e 99'.
  6. Capturando no Lugar Certo: no submit, chame a validação dentro de try e mostre o erro no campo indicado.
  7. Separando os Tipos: no catch, use erro instanceof ErroValidacao para diferenciar dado inválido de falha de programação.
  8. Não Engolindo Erros: para erros desconhecidos, mostre uma mensagem genérica e registre com console.error.
  9. Limpando o Estado: no finally, reabilite o botão e remova o destaque dos campos que ficaram válidos.
  10. Validação e Testes: teste cada regra, o botão 'simular falha interna' e o caminho feliz, e registre no README a diferença entre os tipos de erro.
